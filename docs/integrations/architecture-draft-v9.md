## 1. The decisions on one page

1. **The goal is a sync problem, not an AI problem.** "Connect once, data flows in, the agent works, results flow back" needs a machine identity, provenance (external ids), a durable record of what is still to be sent, a way to send it, and one adapter per named system. MCP does not provide delivery, retries or sync (FACT, https://modelcontextprotocol.io/specification/2026-07-28/changelog: "a broken response stream loses the in-flight request").
2. **Everything lives inside `apps/api-java`, on the same Postgres.** No new service, broker, Redis, Kafka or workflow engine. Reuse `Db.inOrg` and forced RLS, the narrow-lookup pattern, `background_jobs`, `AuthInterceptor` with per-field PII redaction, `AuditService`, `AdviceGuard` and the CSV-import validation (FACT, backend map §2, §3, §5, §6.4, §10).
3. **Order of work:** gate P → prerequisites (0) → results CSV export (A) → then, **only when a pilot confirms which path it will use**, the integration core plus either the named connector (E, Zoho Recruit by default) or the developer surface (Dev: API keys, `/v1`, events feed). Webhooks only if a pilot needs push. Founder decision 1 picks the branch. For a pilot that keeps candidates in Excel or Google Sheets and has no developer, the MVP is CSV in and CSV out, so "connect once" is **not** met for that customer; the follow-up is a Google Sheet connection (section 13.2). **None of it reaches customers until the Java API serves production** (gate P): FACT, production builds and routes only the Nest API (`Dockerfile` line 61 `CMD ["node", "apps/api/dist/main.js"]`; `docker/Caddyfile`). Separately, two risks that exist today whatever happens to integrations are recorded as small separate items, not designed here (section 13.1): item G, self-serve phone calling on the shared number, and item W, workspace deletion leaving provider copies and a database restore bringing back erased people.
4. **Data flows one way per field.** Jobs and candidate contact details flow **in**; call results and human decisions flow **out**. For ATS-linked rows the ATS owns contact fields, and the server enforces that.
5. **The product rule holds at the boundary.** Only facts and decisions a named person made leave HRVoice: never `fitPercent`, a coverage percentage, a score, a rank, "qualified", or a stage the system chose. The stored call summary is written by the voice provider, so **no summary leaves HRVoice** until we write our own (founder decision 4). One serializer builds every outbound body and is tested for this.
6. **Results flow back even if nobody opens HRVoice.** In an org with a live connection, a background job fetches results whose provider webhook was lost. Every phone call the voice provider accepted (it has a conversation id) that ends after the connection exists produces one ATS note (E) or one `call.ended` (Dev), unanswered calls included. A dial that never reached the provider stays inside HRVoice. If no result can be fetched, the customer gets "result unavailable" instead of silence.
7. **Calls start from a person, as today:** one Call click for one candidate, through the existing route and guards. Calling many people with one click is a separate design that is not approved (`later-bulk-calling.md`). Fully automatic calling of imported candidates waits for a written founder decision on consent, calling hours and DND (FACT, `apps/api-java/MIGRATION_STATUS.md` line 373).
8. **Outbound problems never stop inbound data, and one failing item never stops the others.** API keys, intake and the events feed do not depend on whether a customer's ATS write is healthy; each outbound item retries on its own schedule.
9. **MCP:** never inside a live call; never as the sync channel; our own read-only MCP server later, when a paying customer asks.

The honest MVP loop is therefore: **in automatically (once a pilot's system is known), one Call click per person, out automatically.** The founder's "our agents perform the workflow" is met for data in and results out, not for starting calls (R25). Founder decision 10b asks whether that is acceptable for the first pilots at their daily volume, before any pilot is quoted a date.

## 3. Connector abstraction

**RECOMMENDATION.** A connector is one Spring bean implementing `AtsPort`, plus a static `ConnectorSpec`. No plugin loader and no DSL: adapters are registered in a map by key, the same way `JobQueue` handlers register by kind (FACT, `JAVA/notify/Notifications.java` line 49, `JAVA/knowledge/DocumentProcessor.java` line 55).

```java
// Sketch only. Not code to commit.
record ConnectorSpec(String key, String displayName, Auth auth, List<String> scopes,
                     Set<Reads> reads, Set<Action> actions, Budget budget) {}

enum Action {
  ADD_NOTE,   // trigger: a settled call. Content from ExternalPayloads only.
  SET_STAGE   // trigger: a person's decision, read at send time. Never a call outcome, never a model.
}

interface AtsPort {
  ConnectorSpec spec();
  Page<ExternalJob>         listJobs(Conn c, String cursor);
  Page<ExternalApplication> listApplications(Conn c, Instant modifiedSince, String cursor);
  ExternalApplication       getApplication(Conn c, String applicationRef);   // live status and open/closed, for the stage handler
  List<ExternalStage>       listStages(Conn c, String jobRef);              // read live; stages get renamed
  List<Deleted>             deletedSince(Conn c, Instant since);            // permanent deletions only: (applicationRef or candidateRef, deletedAt);
                                                                            // the only evidence of a deletion; empty when unsupported,
                                                                            // and then nothing is erased automatically
  List<String>              noteMarkers(Conn c, ExternalApplication app);  // Zoho: listed on the parent Candidate record
  void addNote(Conn c, ExternalApplication app, String text, String marker); // Zoho: written to the parent Candidate record
  void setStage(Conn c, ExternalApplication app, String stageRef, String comment);
  // Typed errors: RateLimited(retryAfter), AuthRevoked, NotFound, Rejected(fieldErrors), Transient
}
```

- `ExternalJob`, `ExternalApplication`, `ExternalStage`, `Deleted` and `Page` are the whole cross-vendor model; vendor field names never leave the adapter (FACT, rule in `JAVA/voice/VoicePorts.java` lines 7-10). **The adapter maps a vendor body to these records before anything is logged; raw vendor bodies never reach logs, `last_error` or `last_sync_issues`** (round 8 SA-7; FACT: Zoho's deleted-records reply carries `display_name`, `deleted_by.name` and `created_by.name`, https://www.zoho.com/recruit/developer-guide/apiv2/get-deleted-records.html).
- **Zoho notes go on the Candidate record, not the application** (round 8 IA-1, EIA-2, CR-6). FACT: Create Notes supports "candidate, jobopenings, Interview, client, contact, department, task, event, vendor custommodule", not applications, and links a note by `Parent_Id` and `se_module`; its scope is `ZohoRecruit.modules.notes.{operation_type}` (https://www.zoho.com/recruit/developer-guide/apiv2/create-notes.html). So `addNote` and `noteMarkers` use `candidate_links.external_parent_id`; the note's first line names the job, which matters because one candidate can apply to several jobs. Change Status supports "candidate, application, jobopening, and offer" with `ids`, `jobids`, `Candidate_Status` and `comments` (https://www.zoho.com/recruit/developer-guide/apiv2/change-status.html), so `setStage` acts on the application.
- `ExternalJob.description` is plain text: an adapter whose system returns HTML converts it before the create-once copy (FACT: Zoho's sample `Job_Description` is HTML, https://www.zoho.com/recruit/developer-guide/apiv2/get-associated-records.html; Tika's HTML parser is already on the compile classpath, `apps/api-java/pom.xml` line 78).
- Token requests are sent as a form body (FACT, RFC 6749 §4.1.3, https://datatracker.ietf.org/doc/html/rfc6749#section-4.1.3). Adapters never put a URL with a query string into an exception message.
- **HTTP limits for vendor APIs** (round 6 SA-3): connect 5 s, read 30 s, response body read by streaming and capped at 10 MB. The 64 KB / 10 s limits of section 6.4 are for customer-supplied URLs only: a Zoho list page holds up to 200 records (FACT: `per_page` default 200, https://www.zoho.com/recruit/developer-guide/apiv2/get-records.html), which is likely to exceed 64 KB (ASSUMPTION; v9 no longer imports resume text, so the cap is about page size in general).
- The `custom` connection has no adapter. A unified-API vendor (Kombo, Merge) would later be one more `AtsPort`.

Declared capabilities for the systems in view: as v6 §3.2 (Zoho Recruit first; Keka Hire V2; Greenhouse and Lever later through partner programmes; Darwinbox, Naukri RMS, Freshteam later or avoid).

### 6.1 How results are found and delivered

**FACT (code read).**
- `VoiceSessions.apply` writes provider data in one transaction, runs the post-call extractor outside any transaction, may write a filled summary in a second transaction, records the ledger outcome, then publishes in-process events; it runs on every webhook, reconcile and results-page open (`JAVA/voice/VoiceSessions.java` lines 505-551).
- `expireStale` runs every 5 minutes, visits only orgs with `status = 'active'`, returns at once when `ELEVENLABS_ENABLED` is false (the default), and only sets stale sessions to `ended`; it fetches nothing (lines 678-687; `JAVA/platform/Env.java` line 124). Reconcile runs only when a person ends a call or opens the results page (`JAVA/hiring/HiringController.java` line 271).
- A dial the adapter could not complete leaves a `failed` session with no conversation id (`VoiceSessions.java` lines 441-449).
- `apply` calls `scheduleRetry` for a failed phone call, which inserts a `scheduled_calls` row only when the use case enables retry; the hiring use case has `callPolicy.retry.enabled: false` (`usecases/hiring.json` line 136), and no Java code reads `scheduled_calls` (grep: the only reference is that insert, `VoiceSessions.java` line 587). So background fetch through `apply` never starts a call. Switching retry on is a founder decision 10 matter, not a setting change.
- `JobQueue.enqueue` opens its own transaction, so a job cannot be enqueued inside a caller's transaction; `runDue` visits only orgs with `status = 'active'`; a failed handler is retried with backoff and ends `dead` after its attempts (`JAVA/jobs/JobQueue.java` lines 66-75, 93-97, 136-161).
- `Jobs.updateStatuses` sets `candidates.updated_at = now()` whenever the stage changes (`JAVA/hiring/Jobs.java` line 264). The route then writes one `hiring.candidate_status_changed` audit row per candidate, with `from` and `to`, after that transaction, through `AuditService.record`, which logs and swallows failures (`JAVA/hiring/HiringController.java` lines 374, 387, 391-396; `JAVA/audit/AuditService.java`). `Candidates.update` also sets `updated_at` (`JAVA/hiring/Candidates.java` line 113).

**A phone call with a candidate is settled** (`agent_sessions.channel = 'phone'`, `candidate_id` set, **`external_conversation_id` set**, meaning the provider accepted the dial; browser tests never leave) when its status is `ended` or `failed`, `ended_at` is more than 3 minutes ago, and it has a `failure_reason`, or a transcript **and, if the transcript has a user turn, `structured_answers` set**; or `ended_at` is more than 90 minutes ago. The answers condition (round 8 CR-2) is for the lost-webhook path, where `ended_at` was set long before (`VoiceSessions.java` lines 266, 602) and `apply` writes the transcript and, after an LLM call, the answers in two UPDATEs (lines 505-534): a tick between them would send "not answered" for every question. Ceiling: with no answers from provider or extractor, the note waits for the 90-minute deadline. A dial the provider refused, or that failed on our side, is not a call for integrations: it is shown in HRVoice and never written to an ATS, because we cannot know whether it was placed.

**One outcome function (slice 0).** `CallOutcomes.outcome(session)` returns `failure_reason` when set; otherwise `completed` when the transcript has a user turn; `no_conversation` ("Picked up, didn't speak") with a transcript and no user turn; otherwise `result_unavailable` ("We couldn't get this call's result. Open the candidate in HRVoice to try again.") once `ended_at` is more than 90 minutes ago. One value exists only in the app: `content_erased` ("Call content removed"). `Jobs.callStatus`, `queue`, `outcome`, the results route, the results CSV and `ExternalPayloads` all call it (FACT: today `callStatus` maps any `ended` session without a failure reason to `completed`, `JAVA/hiring/Jobs.java` lines 170-178). Queues: `no_conversation` joins "Didn't connect"; `result_unavailable` stays in "Ready for review" with "Try again" (opening results already reconciles); `content_erased` is in no queue.

**Background result fetch (Core; only orgs with a live connection).** Every fifth run, the tick enqueues `fetch_results:<org>` when the org has phone sessions with a candidate and a conversation id that either ended 3 to 60 minutes ago with no transcript and no `failure_reason`, or are still `active` more than `voiceMaxPhoneMinutes + 2` minutes after they started. The handler runs on the integration lane (section 6.8), never on Spring's scheduler thread (FACT: it "uses one thread by default", https://docs.spring.io/spring-boot/3.4/reference/features/task-execution-and-scheduling.html, and one fetch can take 10 s connect plus 30 s read, `HostedVoiceAdapter.java` lines 46-47), and only while voice is on. It passes up to 5 such sessions to **a new method `reconcileSystem(org, vsId)`** (round 7 AM-3, EIA-3, SA-7; FACT: today's only entry point, `reconcile(Actor, vsId)`, reads and audits as the person, `JAVA/voice/VoiceSessions.java` lines 467-483): built from `voice.fetch` and `apply(org, null, ...)`, run as a worker (`inOrg(org, Db.NIL)`, NULL audit actor), returning at once for a session with `content_erased_at` set, and sharing today's skip rule. The 40-second budget is checked **before each session starts** and covers `apply`'s one extraction call; the run stops at the budget or **at the first provider timeout or 5xx**. An extraction failure does not stop the run (FACT: `PostCallExtractor.extract` catches it and returns the provider's data, already stored by `apply`'s first UPDATE, `JAVA/engine/PostCallExtractor.java` lines 69-78). What is left is tried again 5 minutes later: about 12 tries over the hour, no dead rows. A `voice.reconcile` timer records each run. `ponytail:` orgs without a connection keep today's behaviour (a result is fetched when someone opens it).

**Notes (E): level-triggered, one delivery row per (connection, call).**

*Discovery* (the tick, database only, one `inOrg` per org, for each ATS connection that has `connected_at` set and is not `disconnected`, `needs_attention` included): for settled calls whose candidate has a live link on that connection (`remote_state in ('open', 'closed')`), with `started_at > now() - interval '8 days'` (the existing `(organization_id, started_at)` index), `ended_at` within 7 days and later than the connection's `connected_at`, and `content_erased_at IS NULL`, upsert:

```sql
-- Sketch. content_hash = md5(status, failure_reason, transcript is not null, <transcript has a user turn>, structured_answers)
insert into integration_deliveries (organization_id, connection_id, kind, candidate_id, voice_session_id,
                                    content_hash, status, attempts, next_attempt_at)
select ..., 'note', vs.candidate_id, vs.id, <hash>, 'pending', 0, now() from ...
on conflict (connection_id, voice_session_id) do update
  set content_hash = excluded.content_hash, status = 'pending', attempts = 0, next_attempt_at = now(), updated_at = now()
  where integration_deliveries.content_hash is distinct from excluded.content_hash;
```

Only what can leave is hashed (as v6): the summary never leaves, so a summary filled later makes no new version. Then, for each connection with a `pending` row whose `next_attempt_at <= now()`, not inside `rate_limited_until` and with its preconditions met, the tick enqueues `send:<connectionId>`. `ponytail:` rehashes up to 7 days of linked calls a minute per connected org; the upgrade is a dirty flag set by `apply`.

*Sending* (`send:<connectionId>`, on the lane): reload the connection and stop if it is `disconnected` or its sending principal is not live (section 10). Take up to 20 due rows ordered by `next_attempt_at`, **joined so that only rows whose link is live and, for notes, whose call has `content_erased_at IS NULL` are taken** (round 8 EIA-1, BE-1: a row on a `missing` link that was skipped kept its place at the front, so 20 such rows could hold up every other note and spend the customer's Zoho credits on marker reads). A row on a link that is not live waits as it is: it is sent if the link comes back, and expires on the tick otherwise. For each row taken:
1. List the application's note markers (vendor HTTP).
2. **Then, in one short read immediately before the write** (round 7 BE-6), re-read the row, its call and its link, and build the note with `ExternalPayloads` for the sending principal: if the call is erased (`content_erased_at` set), the link is no longer live, or the row is gone, skip it (the erasure path deletes the person's rows; this covers an erasure committed after discovery, round 6 IA-3 / BE-2). The marker carries the rendered note's hash prefix; if it is among the listed markers, write nothing; otherwise `addNote`. A removal that commits during the `addNote` call itself cannot be stopped without holding a lock across vendor HTTP; the DPA and the removal runbook say that a send already in progress can finish within seconds of a removal.
3. **Success** (or the marker existed): `UPDATE ... SET status = 'sent', sent_at = now(), attempts = 0, last_error_code = NULL WHERE id = ? AND content_hash = :hashReadInStep2`. If the hash moved meanwhile, the row stays `pending` and the next run sends the newer version once (the marker stops a duplicate). The connection's `consecutive_failures` resets and `last_success_at` is set.
4. **Permanent refusal** (`Rejected`, `NotFound`, other 4xx except 408 and 429): the row becomes `failed` with its error code, and the run carries on with the next row. Card: "1 call result couldn't be sent to Zoho Recruit. Open it in HRVoice."
5. **Rate limited:** set `rate_limited_until` and stop.
6. **Transient** (timeout, 408, 5xx, `Transient`): `attempts + 1`, `next_attempt_at = now() + least(1 hour, 1 minute × 2^attempts)`; the connection's `consecutive_failures + 1` (`failing_since` on the first; one email to admins at the third: "Couldn't send since 10:40"); **the run stops**, because the vendor is probably in trouble. Rows are taken in `next_attempt_at` order, so a row that always fails moves behind the others and never holds them up: no probe is needed.
7. **`AuthRevoked`:** `needs_attention` (`consent_revoked`) and stop.
8. **Expiry runs on the tick**, as a database step, so it also reaches rows the sender no longer takes: a note row still `pending` 7 days after its call ended, or a stage row still `pending` 7 days after the decision (`candidates.updated_at`; round 7 IA-2, UX-1), becomes `failed` with `expired`; the card says "N call results from before 3 Nov couldn't be sent. Open them in HRVoice." or "N decisions couldn't be set in Zoho Recruit. Set them there by hand." Nothing disappears silently.
9. **Budget:** 20 rows or 120 seconds, far inside the queue's 900-second lease (FACT, `JobQueue.java` line 39); the next tick re-enqueues if rows are still due. The handler never throws for a delivery failure, so queue attempts are spent only on bugs.

Consequences:
- **One note per call** normally; a follow-up note ("Updated result for the call on 3 Oct, 11:02") only when the rendered note changed.
- **Unanswered, failed and silent calls** the provider accepted get a note with their outcome.
- **No backlog on first connect**: the floor is `connected_at`.
- **Disconnect and reconnect** (round 7 EIA-5): discovery skips a `disconnected` connection, and a reconnect moves `connected_at`, so calls that ended while disconnected get no note. Note rows already `pending` when it was disconnected are still sent after the reconnect, up to 7 days after their call: they are results of calls made while connected, and a note never changes anything in the ATS. Stage rows are different: a reconnect re-baselines `pushed_stage`, so no decision from before the reconnect is written (section 7).
- **A connection that needs attention keeps its rows**; they are sent when it recovers, and anything older than 7 days is shown as expired.
- **No order is promised between notes**; each note is about one call (`02-resolutions.md` R3.5: "Strict order is not needed for notes (each note is about one call)").
- **Nest-written results are caught too**, because discovery reads the database.

**The 5-minute loop (Core).** `expireStale` keeps its schedule and its stale expiry, which still follows the voice switch. It gains steps that are **database work only** and run whatever the voice switch says, for every `active` org: the daily retention purge, enqueueing `provider_delete:<org>` when erased calls still hold a conversation id, and, from Dev, the daily events purge (section 6.5). All vendor and provider HTTP runs on the lane, so the scheduler pool needs no change. `ponytail:` one scheduler thread; the tick can lag behind a long inline document job in `JobQueue.poll` (already true for the 5-minute loop today); set `spring.task.scheduling.pool.size` if that lag is ever seen.

**Use-case gate.** Delivery happens only when the use case's `actions.integrations` is `true` (renamed from `webhook`). Stage write-back additionally needs the per-connection opt-in.

### 6.2 The one serializer (`ExternalPayloads`) and the one export rule

### 6.5 Events feed and event log (Dev slice only)

The ordered log exists only for the feed, so it ships only with the developer surface. Rules as already agreed (v6 §6.1 and §6.5), restated:

- **Emitting `call.ended`.** In an org with a `custom` connection that has `connected_at` set and is not disconnected, the tick selects and hashes settled calls since that `connected_at` (within 7 days, `content_erased_at IS NULL`) **without** the events lock; only if a row's hash differs does it take the lock and run `UPDATE voice_sessions SET result_emitted_hash = :h, result_version = result_version + 1 WHERE id = ? AND result_emitted_hash IS DISTINCT FROM :h AND content_erased_at IS NULL RETURNING result_version` (the last condition is round 6's IA-3 / BE-2 fix: an erasure committed between scan and update emits nothing), then `Events.emit(sql, 'call.ended', {version})`.
- **Stage outbox.** In such an org, `Jobs.updateStatuses` takes the org events lock **as its first statement**, before `loadJob` locks the job row, and emits `contact.stage_changed` with `{from, to, decidedByUserId}` inside the existing `if (!previous.equals(...))` branch (FACT: the job row is locked first and this is the only Java writer of `screening_status`, `JAVA/hiring/Jobs.java` lines 255-264; `HiringController.java` lines 373, 386). Orgs without a feed take no events lock, so a recruiter's decision in an E-only workspace never waits on it.
- **Lock and `seq`.** `pg_advisory_xact_lock(hashtextextended('events:' || org, 0))` first in every emitting transaction; `Events.emit` reads `coalesce(max(seq), 0) + 1` and inserts with `created_at = clock_timestamp()` (FACT, https://www.postgresql.org/docs/current/functions-datetime.html); the 15-second `statement_timeout` maps to `ApiError.conflict("events.busy", ...)` as `Db.underAdvisoryLock` already does (FACT, `JAVA/platform/Db.java` lines 103-115). Lock order: the events lock, then the job row, then candidate rows; the sweep takes the events lock, then `voice_sessions` rows. Every transaction is READ COMMITTED (FACT: `Db` sets no isolation level), which the "lock, then read `max(seq)`" rule relies on.
- **Purge.** Once a day per org, from the 5-minute loop's database step: boundary `b = coalesce((select min(seq) ... where created_at >= now() - interval '30 days'), (select max(seq) ...))`, then `DELETE ... WHERE seq < b`. **The `max(seq)` fallback keeps the org's newest event, so `max(seq)` never goes down** and a quiet month cannot reuse numbers a client has passed.
- **Feed** `GET /v1/events?after=<cursor>&types=`: this org's events with `seq > after`, ordered, at most 200, bodies built at read time by `ExternalPayloads` for the calling key. Without `after`: `{items: [], next: <cursor>}` positioned before the hold. The cursor wraps the per-org `seq` and `EVENTS_EPOCH`; a cursor from another epoch gets `410`. **`410 cursor_expired` is defined against the oldest retained `seq`:** if `after < min(seq) - 1`, events after the cursor were purged, and the client is told to restart without `after`; never a silent skip.
- **2-minute hold, cut at a `seq` boundary:** only events whose `seq` is below the lowest `seq` created in the last 2 minutes are returned.
- **`superseded`:** a `contact.stage_changed` carries `superseded: true` when a later stage event exists for the same candidate, so decide, Undo, decide again yields one actionable event. The docs say: act on a stage event only when `superseded` is `false`.
- Contract: at-least-once, ordered within the workspace, events at least 2 minutes old, 30-day window.

### 6.8 Queue changes (Core)

FACT about today's code (`JAVA/jobs/JobQueue.java`): 2 worker threads for every kind and tenant (lines 50-54); `enqueue` always calls `wake()`, which schedules `runScope` for that org on those workers (lines 66-81); `runScope` drains one org until empty, 10 jobs per claim; `poll()` runs `runDue()` inline on Spring's scheduler thread (lines 87-90) and visits only `active` orgs, one transaction each (line 96), under the note "add a due-organizations index table past ~1k orgs"; job rows are visible only inside their org (RLS), so finding work means one transaction per org.

The lane's `@Scheduled` poll (every 30 s) only wakes sleeping threads and **never runs a handler on the scheduler thread**. So a claimed job never waits in a queue, and every job starts well inside its 900-second lease. FACT why: the claim also re-takes `running` rows whose lease has expired (`JAVA/jobs/JobQueue.java` lines 39 and 123), so a job left waiting past 900 seconds would be claimed again and could write the same note twice;
   - every lane handler has a per-run budget (section 6.1) far inside the 900-second lease;
   - the lane honours `JOBS_ENABLED` as `JobQueue.poll()` does today (FACT, `JobQueue.java` `poll`; `Env.java` line 113). `JOBS_ENABLED=false` is the incident switch that stops every vendor and provider call (the tick keeps doing database work; enqueueing is idempotent per key); v8's `AUTOMATION_PAUSED` is removed.

   The tick likewise visits every `active` org in its own transaction and reads that org's live connections there, skipping orgs with none. No cache can go stale across replicas. `ponytail:` one short transaction per org per tick and per idle lane round, like `JobQueue.poll` today; the org count follows sign-ups, not customers (round 8 CR-8), so add a due-orgs table past about 1,000 orgs **or before self-serve sign-up is opened widely**, whichever comes first.
2. **No `Snooze`.** Every lane job is level-triggered: it does what is due within its budget and returns, and the tick (or, for `provider_delete`, the 5-minute loop) enqueues it again while work remains. Two jobs of one org can still run at once on the two threads (for example `pull` and `nightly`); each handler is written for that (the queue key keeps one `send:<conn>` at a time, and the nightly listing marks `missing` only among links read before it started, section 5). 3. **POLICY** `integration` `{5, 30}`; handlers never throw for expected failures, so attempts only cover bugs.
4. **Unknown kinds** throw a clear error at `enqueue`.
5. **Connection pool check** in Core's definition of done: pool size ≥ lane threads (2) + legacy workers (2) + the scheduler thread + 1 connection held by a token refresh across its HTTP call + headroom for web traffic (FACT: pool default 10, `Env.java` line 88).

## 7. Two-way action architecture

```
Integration       integration_connections row (org-scoped, RLS): sending principal, status, config, delivery health
   ▼
Connector         AtsPort adapter + ConnectorSpec: auth type, readable objects, declared actions
   ▼
Available actions spec.actions ∩ enabled in connection.config ∩ use case actions.integrations
   ▼
Automation        fixed rules in code, not a rule builder:
                    a settled call (a fact)                    → ADD_NOTE   (always on for a connected ATS)
                    a person's decision: reviewed / declined   → SET_STAGE  (opt-in, customer-mapped, level-triggered, from a baseline)
                    custom connection                          → events feed (webhooks later)
   ▼
Agent             the voice agent never calls an action. It receives only the compiled job, questions and knowledge.
```

**Provider independence of the core agent.** FACT: data reaches a live call only at provisioning, and the live agent gets only `end_call`, `voicemail_detection` and `transfer_to_number` (`JAVA/engine/CallContextCompiler.java` lines 26-37, 220-237).

**Where the never-recommend rule is enforced (three places, all testable):** content (only `ExternalPayloads`, no summary); trigger (`SET_STAGE` sends only the candidate's current `screening_status`, only `reviewed` or `declined`, set only by a person through the stage routes, FACT `JAVA/hiring/Jobs.java` line 264; API keys cannot change stages; a call outcome never moves an ATS status); target (adapters expose only `addNote` and `setStage`). The live call itself is protected by the prompt fence fix (section 11.1 item 9).

**Stage write-back (from a baseline, level-triggered).** Off by default. The customer picks the target status for "Moved forward" and "Not moving forward" from their live status list.
- **Baseline.** Only decisions made after write-back is on, or after a row was linked, are sent (`pushed_stage` as section 2.3). Earlier decisions are never sent in bulk. **A reconnect re-baselines too** (round 7 CR-1, UX-1): the transaction that moves `connected_at` runs the same UPDATE as switching write-back on (`pushed_stage` = the current stage for the connection's links), so decisions made while the card said "Not connected" are never written; the reconnect screen says "Decisions made while disconnected are not sent to Zoho Recruit." **That UPDATE also closes the connection's `pending` and `failed` stage rows** (`status = 'sent'`, `last_error_code = 'skipped'`, `content_hash` = the link's new `pushed_stage`), so no card line or Retry is left for a decision the screen said would not be sent (round 8 BE-6). Recovering from `needs_attention` (new consent, Take over) does not re-baseline: those decisions were made while the footer promised a write, and they are still sent, under the rules below and the 7-day expiry.
- **Discovery** (the tick, for connections that are not `disconnected`, have write-back on and are not `needs_attention` with `status_unmapped`): candidates with a live link where the current stage is `reviewed`/`declined` and differs from `pushed_stage`, or is `new`/`screening` while `pushed_stage` is `reviewed`/`declined`. Upsert their stage row: `content_hash` = the current stage, `status = 'pending'`, `attempts = 0`, `next_attempt_at = candidates.updated_at + interval '2 minutes'` (the hold), when `content_hash` differs.
- **The handler** (inside `send:<connectionId>`, same refusal and backoff rules as notes):
  1. **Hold.** If `candidates.updated_at` is less than 2 minutes ago, move `next_attempt_at` to 2 minutes after it and leave the row. The in-app Undo lasts 8 seconds and re-posts the previous stage (FACT, `apps/web/components/ui/toaster.tsx` line 78; `apps/web/app/jobs/[id]/candidates/page.tsx` lines 680-698), which moves `updated_at` again. A person's contact edit also moves it (FACT, `JAVA/hiring/Candidates.java` line 113); that only delays the push. The pull never moves it (section 5). Otherwise read the candidate's current stage **S** and the row's hash **H**.
  2. **Switch, read at send time, and nothing to send** (round 7 BE-1). The run has reloaded the connection: if write-back is now off, S is `reviewed`/`declined` and its target status is not mapped, or the use case's `actions.integrations` is `false`, close the row without calling the ATS (`skipped`). Close it the same way if S equals `pushed_stage` (for example, undone within the hold), or if S and `pushed_stage` are both `new`/`screening` (nothing was ever sent).
  3. **Read the application live** (`getApplication`: its status, and whether it is open or closed in the ATS).
     - **Already at target** (S is `reviewed`/`declined`): its status equals the mapped target of S (for example our own write just before a crash): no note, no `setStage`.
     - **Forward** (S is `reviewed`/`declined`): call `setStage` with the comment "Moved forward by Priya Sharma in HRVoice" **only if the application is open and its live status is either the connection's trigger status (where it was when we brought it in) or the mapped target of `pushed_stage` (the status HRVoice last wrote)**. In every other case write a note instead and leave the status alone (`note_only`): "Not moving forward (decided by Priya Sharma in HRVoice). The status in Zoho Recruit was left as it is; update it there if needed." ("Moved forward" likewise). The note makes no claim about who set the current status, so it is true whether the status was moved on in the ATS, the application is closed there, the trigger status was changed in HRVoice, or an earlier decision was withdrawn (round 8 IA-3, CR-5). FACT why not compare with `remote_status_seen`: every 15-minute pull refreshes it for every linked application (section 5), so that check caught only changes made since the last pull (round 7 CR-1, UX-1, EIA-2). `remote_status_seen` is for display only.
     - **Withdrawn** (S is `new`/`screening` while `pushed_stage` is `reviewed`/`declined`): a note "Decision withdrawn in HRVoice by Priya Sharma. The status in Zoho Recruit was left as it is." (`note_only`).
  4. **One rule for every close** (round 7 IA-1; round 8 BE-3, IA-3, CR-4). First `pushed_stage` := S, **written unconditionally**: it records what this run handled, even if the decision changed during the call to the ATS. Then the row: `status = 'sent'`, `sent_at`, `attempts = 0`, `last_error_code` (NULL, `note_only` or `skipped`) and `content_hash = S`, as a compare-and-set on H. So a later decision always differs from the stored hash and is discovered (decide, Undo, decide again sends exactly once); a decision made during the send leaves the row `pending`, and the next run judges it against the status that was really written; and a row closed at step 2 is not rediscovered every minute, because its hash and `pushed_stage` both equal the current stage. A row that fails permanently or expires keeps its target as its hash, so it is not retried until the decision changes.
- **The allowlist is deliberately not widened** to both mapped targets (round 8 IA-3 a): customers usually map "Moved forward" to a status their team also sets by hand, so a decline in HRVoice would overwrite a move made in Zoho and could email a rejection (the round-7 CR-1 harm). Cost: a written decision that is withdrawn and later reversed arrives as a note, and the decision line says so.
- **The decider's name** (round 7 SA-5, BE-2) comes from the latest `hiring.candidate_status_changed` audit row for that candidate and job **whose `from` differs from its `to`**, used only if that row's `to` equals the stage being sent: the person's display name (`users.name`). Otherwise, or when the name is empty or the row is missing, "a team member". Never an email. FACT: the route writes an audit row for every update in the request, including ones that did not change the stage, after the stage transaction, and `AuditService.record` swallows failures (`JAVA/hiring/Jobs.java` lines 255-269; `JAVA/hiring/HiringController.java` lines 362-396; `JAVA/audit/AuditService.java`). So a no-op re-post by Bob cannot be named as the decision, and when Bob's real change has no audit row, the newest real change points at some other stage and the comment says "a team member", never an earlier decider.
- Because the handler reads current state, retries cannot leave the ATS on an older decision.
- `ponytail:` if a customer's ATS moves new applications on by itself after import (an automation), every decision for those people arrives as a note, not a status. Upgrade if a pilot hits it: store the ATS status the decider saw on the stage row and allow overwriting exactly that (round 7 UX-1's column).

**Notes.** One per call, a follow-up only if the rendered note changed (section 6.1):

```

Outcome: Call completed            (or: No answer / Reached voicemail / Picked up, didn't speak / Number not valid / Result unavailable)
```

16. **(item W, a risk that exists today; new in v9)** When must workspace deletion remove the provider's recordings, transcripts and hosted agents and the stored documents, erasures be re-applied after a database restore, and one deleted document lose its stored file? How long do backups keep erased data, and how long are erasure records kept (as long as the longest backup window plus a margin, round 8 SA-2)? **Recommendation: before the first paid customer or general availability, whichever comes first**; until then the DPA states the gaps (section 13.1 item W).

## 18. ADR-010 contents (to lift verbatim)

Every rule below is stated, with its evidence, elsewhere in this document.

**Gates**
1. Gate P: Java serves production before any slice ships there; it includes the adapter fix-up, one external uptime monitor and the R18 live check, whose failure blocks quoting E until the founder picks a fix (section 13.1).
2. Core is built only together with E or Dev, after ADR-010 is written, and goes live only once Nest is no longer routed in production (section 13.1).
3. The retention, erasure and DPDP items go live before the first external connection (section 11.1 item 10).
4. Item G (founder decision 15) before self-registered workspaces place calls, recommended no later than gate P; item W (founder decision 16, workspace deletion and restore) recommended before the first paid customer or general availability. Both are risks that exist today and are not designed in this plan (section 13.1).

**Tenancy and identity**
5. Every new table: forced RLS on `organization_id = current_org_id()`, listed in `StructuralTest`; every foreign key `ON DELETE CASCADE`; no bypass; the tenant comes only from server state (sections 2.3, 10).
6. API keys work only on `/v1` handlers, only as a bearer header, only on `API_PUBLIC_HOST`; the principal type is chosen by the matched handler; effective permissions = key ∩ creator's live permissions; `AuthResolver.membership` checks the user, the workspace and the membership (Dev; sections 6.6, 10).
7. Code reachable from `/v1` never re-reads `role_permissions` (section 10).
8. Workers run `inOrg(org, Db.NIL)` and audit with a NULL actor (section 10).

**Product rule**
9. Only `ExternalPayloads` builds outbound bodies: no summary; no score, coverage, rank or recommendation; answers only to the job's own questions, scrubbed, plain text; public decision values; display names, never emails; one export rule (section 6.2).
10. Only a person's decision moves an ATS status: opt-in, re-checked at send time, after a 2-minute hold, from a baseline that a reconnect resets (closing older stage rows), reading current state, checking "already at target" first; `setStage` only on an open application whose live status is the trigger status or the status we last wrote, otherwise a note whose wording claims nothing about who set the current status; every close sets `pushed_stage` (unconditionally) and the row's hash (compare-and-set) to the stage the run handled; the pull never moves `candidates.updated_at`; the decider is named only from a real stage change to that stage (section 7).
11. The job title and description (in the role fence), retrieved passages and company facts are fenced before they reach a prompt (slice 0); agent linking stays human-only (section 11.1 item 9).

**Delivery (Core + E)**
12. Outbound to an ATS is level-triggered: one `integration_deliveries` row per (connection, call) and per (connection, candidate) for stages; no order is promised; each item backs off on its own; the sender takes only rows on live links and unerased calls; a run stops at the first transient failure; a note unsent 7 days after its call, or a stage push 7 days after its decision, is marked `expired` by the tick and shown. Zoho notes go on the Candidate record (sections 3, 6.1, 7).
13. A call is settled when it has a failure reason, or a transcript (with answers stored if a user spoke), or 90 minutes have passed; one `CallOutcomes.outcome` serves the app and every body; a dial with no conversation id never leaves (section 6.1).
14. Erased calls never leave: discovery, the sender and the Dev sweep's update all require `content_erased_at IS NULL` (sections 6.1, 6.5).

**Events (Dev only)**
15. In an org with a feed, every emitting transaction takes the org events lock as its first statement; lock order: the events lock, then the job row, then candidate rows (section 6.5).
16. `seq` is per org with `created_at = clock_timestamp()` after the lock; the purge cuts below a `seq` boundary and always keeps the newest event; `410` when the cursor is below the oldest retained `seq` minus one; cursors carry `EVENTS_EPOCH`; a stage event followed by a later one for the same candidate is `superseded` (section 6.5).

**Calls and background work**
17. Every dial goes through `startOutbound` and `dialLocked` and their existing guards, plus the closed-in-ATS block in `dialLocked` (`candidates.closed_externally`); item G's workspace and email checks sit in `startOutbound`; this plan adds no bulk or automatic dialing (sections 5, 10, 13.1).
18. The tick and the 5-minute loop do database work only; every vendor and provider HTTP call runs on the integration lane, with a per-run budget checked before each item, stopping at the first timeout or 5xx; each lane thread claims only the job it runs at once, so no claimed job waits past its lease; the lane's poll never runs a handler on the scheduler thread; integration jobs never wake the general workers; no in-memory org registry is kept; the lane honours `JOBS_ENABLED` (sections 6.1, 6.8).
19. `JOBS_ENABLED=false` is the incident switch for the lane; there is no separate pause switch (section 6.8).

**Data protection**
20. One erasure path. `apply` returns early for erased calls. Anonymisation replaces the person's name with a placeholder and clears their phone, email and resume text. An anonymised ATS link keeps only its suppression hash; `INTEGRATIONS_HASH_KEY` is never rotated. A person is anonymised because of an ATS deletion only when the vendor's **permanent** deletion list shows the application or its candidate, past the grace period, re-checked in the anonymise transaction; absence, a recycle-bin entry or an error reply never erases. `missing` is set only from a complete listing. A row waiting to be anonymised is never adopted, and adoption needs a name match. Connection rows are never deleted while the workspace exists; workspace deletion revokes the vendor tokens. Provider retention is sent with `apply_to_existing_conversations: false` and is part of the context hash. Raw vendor bodies never reach logs. Workspace-level cleanup and re-applying erasures after a restore are item W, outside this plan (sections 3, 5, 11.1 items 10, 13).
21. Audit rows store route templates, never query strings; audit rows are kept, and the DPA says so (section 11.1 items 7, 10).
22. Until Nest is no longer routed in production, migrations only add things Nest ignores (R10).
