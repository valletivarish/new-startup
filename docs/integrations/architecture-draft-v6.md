## 1. The decisions on one page

1. **The goal is a sync problem, not an AI problem.** "Connect once, data flows in, the agent works, results flow back" needs: a machine identity, provenance (external ids), a durable record of what happened, a way to send it out, and one adapter per named system. MCP does not provide delivery, retries or sync (FACT, https://modelcontextprotocol.io/specification/2026-07-28/changelog: "a broken response stream loses the in-flight request").
2. **Everything lives inside `apps/api-java`, on the same Postgres.** No new service, broker, Redis, Kafka or workflow engine. Reuse `Db.inOrg` and forced RLS, the narrow-lookup pattern, `background_jobs`, `AuthInterceptor` with per-field PII redaction, `AuditService`, `AdviceGuard`, the CSV-import validation and the existing `scheduled_calls` table (FACT, backend map §2, §3, §5, §6.4, §10).
3. **Order of work:** prerequisites → results CSV export → "Call selected (N)" with background reconcile for every org → then, **only when a pilot confirms which path it will use**, the integration core plus either the named connector (Zoho Recruit by default) or the developer surface (API keys, `/v1`, events feed). Signed webhooks follow only if a pilot needs push. Founder decision 1 picks the branch. For a pilot that keeps candidates in Excel or Google Sheets and has no developer, the MVP is still CSV in and CSV out, so "connect once" is **not** met for that customer; the follow-up is a Google Sheet connection, sized as its own slice (section 13.2). **None of it reaches customers until the Java API serves production** (gate P, section 13.1): FACT, production today builds and routes only the Nest API (`Dockerfile` line 61 `CMD ["node", "apps/api/dist/main.js"]`; `docker/Caddyfile` routes `/backend/*`, `/webhooks/*`, `/health` and `/api/auth/*` to `api:3001`).
4. **Data flows one way per field.** Jobs and candidate contact details flow **in**. Call results and human decisions flow **out**. For ATS-linked rows the ATS owns contact fields, and the server enforces that.
5. **The product rule holds at the boundary.** Only facts and decisions a named person made leave HRVoice. Never `fitPercent`, a coverage percentage, a score, a rank, "qualified", or a stage the system chose. The call summary we store today is written by the voice provider, not by our no-judgement instruction, so **no summary leaves HRVoice** until we write our own (founder decision 4). One serializer builds every outbound body and is tested for this.
6. **Results flow back even if nobody opens HRVoice.** Background reconcile repairs a lost provider webhook for every org. Every phone call the voice provider accepted (it has a conversation id) that ends after a connection exists produces exactly one `call.ended`, including unanswered ones. A dial that never reached the provider stays inside HRVoice. If no result can be fetched, the customer gets "result unavailable" instead of silence.
7. **Calls start from a person.** Either one Call click, or one confirmed "Call selected (N)" that queues the chosen people. Each queued row is dialed at most once; a dial the voice provider refused for capacity was never placed, so it is not a dial. Every workspace shares one voice-provider account, so bulk dials across all workspaces stay under one platform ceiling. Fully automatic calling of imported candidates waits for a written founder decision on consent, calling hours and DND (FACT, `apps/api-java/MIGRATION_STATUS.md` line 373).
8. **Outbound delivery problems never stop inbound data.** API keys, intake and the events feed do not depend on whether a customer's endpoint or ATS write is healthy.
9. **MCP:** never inside a live call; never as the sync channel; our own read-only MCP server later, when a paying customer asks.

The honest MVP loop is therefore: **in automatically (once a pilot's system is known), call with one click per batch, out automatically.**

## 3. Connector abstraction

**RECOMMENDATION.** A connector is one Spring bean implementing `AtsPort`, plus a static `ConnectorSpec`. No plugin loader and no DSL: adapters are registered in a map by key, the same way `JobQueue` handlers register by kind (FACT, `JAVA/notify/Notifications.java` line 49, `JAVA/knowledge/DocumentProcessor.java` line 55).

```java

record ConnectorSpec(
```

## 6. Outbound: events, feed, notes, CSV

### 6.1 How events are created and delivered

**FACT (code read).**
- `VoiceSessions.apply` writes provider data in one transaction, runs the post-call extractor outside any transaction, may write a filled summary in a second transaction, records the ledger outcome (`completed` when a user turn exists, else `no_conversation`, or the failure), then publishes in-process events; it runs again on every webhook, reconcile and results-page open (`JAVA/voice/VoiceSessions.java` lines 505-551).
- The scheduled `expireStale` runs every 5 minutes for every active org but only sets stale sessions to `ended` (phone after `voiceMaxPhoneMinutes + 10` = 30 minutes by default); it fetches nothing (lines 263-271, 678-687; `JAVA/platform/Env.java` line 131). Reconcile runs only when a person ends a call or opens the results page (`JAVA/hiring/HiringController.java` line 271).
- `markFailed` and the `call_initiation_failure` branch set `ended_at` and `failure_reason` and publish no event (lines 354-358, 649-666).
- `Jobs.updateStatuses` first locks the job row (`loadJob(sql, actor, jobId, true)` appends `for update`, `JAVA/hiring/Jobs.java` lines 64-67, 256-257), then reads `previous` with a plain SELECT (lines 258-260). Candidates are job-scoped, and this is the only Java writer of `screening_status` (both stage routes call it, `JAVA/hiring/HiringController.java` lines 373, 386), so Java stage changes on one job are already serialised and `from` is exact (v5 said otherwise; Round 5 BE-5).
- `Db.inOrg` always opens a new transaction (`REQUIRES_NEW`, `JAVA/platform/Db.java` lines 28-30, 48). `Db` sets no isolation level, so every transaction runs at Postgres's default READ COMMITTED; the "lock, then read `max(seq)`" rule below depends on that. If `Db` ever moves to REPEATABLE READ, the lock must stay a separate statement taken before the snapshot.
- A dial the adapter could not complete is returned as a refused dial with a reason guessed from the error text, and `dialLocked` marks the session `failed` with no conversation id (`JAVA/voice/HostedVoiceAdapter.java` lines 253-272; `VoiceSessions.java` lines 441-449). If the provider did place that call, its webhook finds no session and is ignored (`VoiceSessions.webhook`, line 639).
- The adapter calls the provider through Spring's `RestClient`, which throws on a 4xx or 5xx reply (FACT, https://docs.spring.io/spring-framework/reference/integration/rest-clients.html); `dial` catches every `RuntimeException` and classifies its text (`HostedVoiceAdapter.java` lines 253-272). No pattern in `CallOutcomes.fromDialFailure` matches the provider's 429 messages `too_many_concurrent_requests` or `system_busy` (`\bbusy\b` does not match after an underscore), so a capacity refusal becomes `unknown`, the session is marked `failed`, and it counts toward the org's daily cap because `counts()` counts every phone session started today (`JAVA/engine/CallOutcomes.java` lines 22-46; `VoiceSessions.java` lines 263-280, 441-457). FACT: the provider documents both 429 messages, "exceeded the concurrency limit for your subscription" and "retry the request" (https://help.elevenlabs.io/hc/en-us/articles/19571824571921-API-Error-Code-429).
- The outbound-call reference documents the request fields `agent_id`, `agent_phone_number_id` and `to_number` (all required), a 200 body with `success`, `message`, `conversation_id` and `callSid`, and only a 422 error (FACT, https://elevenlabs.io/docs/api-reference/integrations/twilio/outbound-call). An over-capacity refusal may therefore arrive as `success: false`, not as a 429.
- The application role has no DELETE on `voice_sessions` (FACT, `MIG/0014_elevenlabs_rls.sql`), and `vs_session_fk` is `ON DELETE RESTRICT` (`MIG/0013_elevenlabs_foundation.sql` line 66).
- `expireStale` returns at once when `ELEVENLABS_ENABLED` is false, which is the default (FACT, `VoiceSessions.java` lines 678-680; `JAVA/platform/Env.java` line 124).

**The 5-minute loop (slice A2; background reconcile for every org).** `expireStale` keeps its schedule, but it no longer returns when voice is off; only its provider steps do. Each run, in this fixed order:
1. **Database step, always** (also with `ELEVENLABS_ENABLED=false`), for every active and `deleting` org: the stale expiry it runs today; from Core, erasure batches, the once-a-day events purge and retention purge, and the deleting-org step (section 11.1 item 10). Short statements, no provider HTTP.
2. **Reconcile, only while voice is on, at most 40 seconds:** phone sessions with a candidate and an `external_conversation_id` that are either
   - `ended` 3 to 60 minutes ago with no transcript and no `failure_reason`, or
   - still `active` and started more than `voiceMaxPhoneMinutes + 2` minutes ago (the provider webhook is late or lost),

   are passed to `reconcileSystem(org, vsId)` (the existing fetch plus `apply(org, null, ...)`), at most 5 per org per run.
3. **Provider deletes, only while voice is on, the rest of a 60-second run and never less than 15 seconds:** conversation deletes for erased calls, hosted-agent deletes for `deleting` orgs, and idle stale job agents (section 11.1 item 10).

**Budget and fairness:** steps 2 and 3 each start at a rotating offset in the org list, so every org is reached within a few runs; a failure on one item skips that item; two provider timeouts or 5xx replies in a row (the provider itself is in trouble) end that step; what is left waits for the next run. A `voice.reconcile` timer records each run (VoiceSessions already uses Micrometer counters, lines 183 and 191), and the loop records its heartbeat (section 6.8 item 8). The loop itself is the retry: about 12 tries over the hour, no queue job, no dead rows. `AUTOMATION_PAUSED` skips steps 2 and 3.

This ships in A2 **together with** `spring.task.scheduling.pool.size: 3`, one thread per `@Scheduled` method (`JobQueue.poll`, this loop and the `DocumentProcessor` sweep: FACT, grep of `@Scheduled` in `apps/api-java/src/main`), and a test that fails when the number of `@Scheduled` methods exceeds the configured pool size. Core adds the 60-second tick and raises the pool to 4. FACT why: Spring Boot's scheduler "uses one thread by default" (https://docs.spring.io/spring-boot/3.4/reference/features/task-execution-and-scheduling.html); the repo is on Boot 3.4.5 (`apps/api-java/pom.xml` line 9) and `application.yml` sets no pool; `JobQueue.poll` runs jobs inline on that thread (`JAVA/jobs/JobQueue.java` lines 87-90) and `DocumentProcessor` has a `@Scheduled` sweep too (line 248). With one thread, a provider outage (10 s connect plus 30 s read per fetch, `HostedVoiceAdapter.java` lines 46-47) would hold up the email and document safety net. `ponytail:` inline fetches, single replica (ADR-006); wrap each org in `pg_try_advisory_xact_lock` if a second replica is ever added.

**A phone call with a candidate is settled** (`agent_sessions.channel = 'phone'`, `voice_sessions.candidate_id` set, **`external_conversation_id` set**, meaning the provider accepted the dial; browser test calls never emit) when:
- its status is `ended` or `failed`, **and**
- `ended_at` is more than 3 minutes ago (time for the post-call extractor), **and**
- it has a `failure_reason` or a transcript, **or** `ended_at` is more than 90 minutes ago. A summary or answers alone do not settle a call: the summary never leaves, and the outcome function below needs a failure reason or a transcript, so every emitted version has a defined outcome (Round 5 BE-3).

A dial the provider refused, or that failed on our side, is **not a call** for integrations: it is shown in HRVoice (and as an A2 skip reason) and never written to an ATS as "Call didn't connect", because we cannot know whether the provider placed it (FACT above). Erased calls are excluded by `content_erased_at` before their conversation id is cleared.

**One outcome function (slice 0), used by the app and every body.** `CallOutcomes.outcome(session)` returns: `failure_reason` when set; otherwise `completed` when the transcript has a user turn; `no_conversation` ("Picked up, didn't speak") when there is a transcript with no user turn; otherwise `result_unavailable` ("We couldn't get this call's result. Open the candidate in HRVoice to try again.") once `ended_at` is more than 90 minutes ago. This reuses the ledger's own `completed` / `no_conversation` rule. Two values exist **only in the app**, because their calls never leave: `content_erased` ("Call content removed") and `dial_uncertain` ("We lost contact while placing this call. They may have been called; ask before calling again.") for a `failed` session with reason `network` and no conversation id. **Slice 0 makes the adapter decide `network` from the transport, not from the text:** no reply, a timeout, an I/O error or a 5xx is `network`, because the call may have been placed; any 4xx reply or a `success: false` body means the provider answered and did not place the call, so it keeps its classified reason and is never `network` (a text match on "timeout" there becomes `unknown`). A definite refusal then shows "Call didn't connect", and older `unknown` rows are not relabelled. FACT why: `dial` passes both a `success: false` message and any caught exception's text to `CallOutcomes.fromDialFailure`, which falls through to `unknown` (`HostedVoiceAdapter.java` lines 253-272; `CallOutcomes.java` lines 37-47). `Jobs.callStatus`, `Jobs.queue`, `Jobs.outcome`, the results route and `ExternalPayloads` all call it (FACT: today `callStatus` maps any `ended` session without a failure reason to `completed`, `JAVA/hiring/Jobs.java` lines 170-178, and the web shows a call with no results as "Writing up the call", `apps/web/lib/status-labels.ts` lines 165-176). Queues: `no_conversation` joins "Didn't connect"; `result_unavailable` stays in "Ready for review" with "Try again" (opening results already reconciles); `content_erased` is in no queue; `dial_uncertain` is in "Didn't connect" but never in the "didn't connect" bulk shortcut (section 13.1).

**Outcome sweep (Core).** The 60-second tick runs the sweep **inline**, one `inOrg` per org with a connection that has `connected_at` set and is not `disconnected` (status `needs_attention` included). It does only database work, so it is not queued behind the outbound lane's vendor HTTP. It first selects and hashes settled calls **without** the events lock, so a person's decision never waits behind the scan, with:
- `started_at > now() - interval '8 days'` (uses the existing `(organization_id, started_at)` index) and `ended_at` within 7 days;
- `ended_at` later than the **earliest `connected_at` of the org's connections that are not disconnected** (`connected_at` is set on first `active`, so a connection abandoned half-way through OAuth starts nothing, and reconnecting after a disconnect never replays earlier calls);
- `content_erased_at IS NULL`;
- `result_emitted_hash IS DISTINCT FROM md5(status, failure_reason, transcript is not null, <the transcript has a user turn>, structured_answers)`.

**Only what can leave HRVoice is hashed.** The outcome needs status, failure reason and whether a transcript and a user turn exist; the answers are the only content. The summary is not hashed, because it never leaves (section 6.2), so a summary filled later by the extractor or by a late provider webhook makes no new version. Raw answers stand in for the scrubbed ones: scrub is deterministic, so equal raw answers give equal outbound answers.

Only if at least one row's hash differs (usually none) does it take the org's events lock; then, for each such row: `UPDATE voice_sessions SET result_emitted_hash = <hash>, result_version = result_version + 1 WHERE id = ? AND result_emitted_hash IS DISTINCT FROM <hash> RETURNING result_version` (the compare-and-set re-checks the row under the lock), and only if a row came back, `Events.emit(sql, 'call.ended', ...)` with `{version}`. `ponytail:` rehashes up to 7 days of calls every minute per connected org; the upgrade is a `result_dirty` flag set by `apply`.

Consequences:
- **One `call.ended` per call** in the normal case; a second version only when the result changes after it was sent. Bodies always show the call's current state; receivers keep the latest `version`.
- **Unanswered, failed and silent calls** the provider accepted emit, with their outcome.
- **No backlog on first connect**, and no duplicate after the 30-day purge (the dedupe is on the call row, and the sweep never looks back more than 7 days).
- **A connection that needs attention keeps its history.** The sweep does not depend on the connection being `active`, so events keep being recorded and are sent when it recovers.
- **Nest-written results are caught too**, because the sweep reads the database.

**Stage changes are a true outbox.** `Jobs.updateStatuses` keeps its job-row lock, which already makes `from` exact (FACT above); no extra candidate lock is added. When the org has a connection that has been active and is not disconnected, it takes the org events lock **as its first statement**, before `loadJob` reads the job row, and calls `Events.emit(sql, 'contact.stage_changed', ...)` with `{from, to, decidedByUserId}` inside the existing `if (!previous.equals(new))` branch. No-op changes emit nothing. The free-text reason is not sent outside.

**Ordering lock and per-org `seq`.** Rule: **every emitting transaction takes `pg_advisory_xact_lock(hashtextextended('events:' || org, 0))` before touching any row.** `Events.emit` takes it again (a no-op when already held), reads `coalesce(max(seq), 0) + 1` for the org and inserts with `created_at = clock_timestamp()`, the time after the lock was granted, so `created_at` rises with `seq` inside an org (FACT: `clock_timestamp()` changes during a statement, `now()` is the transaction start, https://www.postgresql.org/docs/current/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT). The lock wait is bounded by the 15-second `statement_timeout` (FACT, `JAVA/platform/Env.java` line 89); `Events` maps its SQLState 57014 to `ApiError.conflict("events.busy", "This is busy right now. Try again in a few seconds.")`, the same mapping `Db.underAdvisoryLock` already does (FACT, `JAVA/platform/Db.java` lines 103-115), so a person's decision never fails with a 500. The lock is released only at commit or rollback (FACT, https://www.postgresql.org/docs/current/explicit-locking.html), so inside one org events commit in `seq` order and a rolled-back number is simply reused. Taking the lock first everywhere gives one lock order: **the events lock, then the job row, then candidate rows** for stage changes; the events lock, then `voice_sessions` rows, for the sweep; `apply`, the dial path and erasure never take the events lock. So two bulk stage changes cannot deadlock on it. Because a rolled-back number is reused, `seq` has no gaps. **`seq` never goes down:** the purge always keeps each org's newest event (below), so after a quiet month the next event still gets a higher number than any cursor already handed out.

**Delivery: one drain per sending connection (E, and later webhooks).** Only connections that send (an ATS, or a configured webhook endpoint) have a drain, a `fanout_seq` and a sending principal; a `custom` connection that only serves the feed has none. The tick enqueues `drain:<connectionId>` when the org's maximum `seq` is above the connection's `fanout_seq`, the connection is active or needs attention for a reason that does not stop sending, its sending principal is live and it is not inside a backoff. The handler:
1. reads up to 20 events with `seq > fanout_seq`, in order;
2. skips, and advances the cursor past, types this connection does not take (an ATS takes `call.ended` notes; stage write-back is separate, section 7) and events whose candidate has no live link on this connection: no link at all (a person added by hand or by CSV to a linked job), or a link with `remote_state = 'deleted'` (removed in the ATS, or anonymised in HRVoice). No delivery row is written for a skip, and the call's delivery line shows nothing;
3. builds the body with `ExternalPayloads` for the sending principal and sends it;
4. on success, or a permanent refusal (`Rejected`, `NotFound`, other 4xx), writes an `integration_deliveries` row and advances `fanout_seq` **in the same transaction, by compare-and-set** (`UPDATE ... SET fanout_seq = :new WHERE id = ? AND fanout_seq = :old`; if no row is updated, the run stops); resets `consecutive_failures`, sets `last_success_at`;
5. on `RateLimited`, returns `Snooze(retryAfter)`;
6. on a timeout, 408, 429, 5xx or `Transient`, increments `consecutive_failures` (setting `failing_since` on the first), and returns `Snooze(60)`; from the third failure on, `Snooze(300)` and one email to admins ("Couldn't send since 10:40");
7. **one bad event:** from the third failure of the same head event on, the run sends the head and then **the next event** once. If the head fails and the next succeeds, the connection works and the head is the problem: the head gets an `integration_deliveries` row with status `failed` and its error code, the cursor moves past both, and the card shows "1 call result couldn't be sent to Zoho Recruit. Open it in HRVoice." If both fail, it is an outage: back off as in step 6, and nothing is marked failed. With no next event yet, the head is retried every 5 minutes until one arrives;
8. on `AuthRevoked`, sets `needs_attention` (`consent_revoked`) and returns;
9. **budget:** a run stops after 20 events or 120 seconds and returns `Snooze(0)`. That is far inside the queue's 900-second lease (FACT: a `running` row whose lease has expired is claimed again, `JAVA/jobs/JobQueue.java` lines 39, 116-134), so two workers never drain one connection at once; the compare-and-set is the backstop.

The drain never throws for a delivery failure, so queue attempts are spent only on bugs. One queue row per connection means one probe at a time and nothing waking up per event. Order is kept per connection, except that an event recorded `failed` by step 7 is passed. `ponytail:` no per-event resend; the person opens that result in HRVoice. Add a resend if a pilot asks.

**Purge.** Once a day per org, from the database step of the **existing 5-minute loop**, which visits every active org (`VoiceSessions.expireStale`, lines 678-687) and from v6 runs even when voice is off, so an org whose connections were all disconnected is purged too. In one transaction under the org's events lock:
- the boundary `b` = `coalesce((SELECT min(seq) FROM integration_events WHERE created_at >= now() - interval '30 days'), (SELECT max(seq) FROM integration_events))` (RLS limits both to the org). Purging below a `seq` boundary, not by age, can never remove a later event and keep an earlier one, and the `max(seq)` fallback **keeps the org's newest event**;
- for each sending connection with `fanout_seq < b - 1`: `UPDATE ... SET fanout_seq = greatest(fanout_seq, b - 1), missed_until = <created_at of event b - 1> WHERE id = ? AND fanout_seq < b - 1`, so a drain that moved the cursor meanwhile is never moved back, and `missed_until` is set only when the cursor really moved. The status card then says "Results of calls before 3 Nov could not be sent. Open them in HRVoice.";
- `DELETE FROM integration_events WHERE seq < b`; `DELETE FROM integration_deliveries WHERE created_at < now() - interval '30 days'`.

Nothing disappears silently.

**Use-case gate.** Emission and delivery happen only when the use case's `actions.integrations` is `true` (renamed from `webhook`). Stage write-back additionally needs the per-connection opt-in.

### 6.4 Delivery health and SSRF

- **Delivery health is not connection status.** The drain's failure counters (section 6.1) drive the "Couldn't send since 10:40" line, the email and the backoff. "Retry" resets `consecutive_failures`, sets the queued drain row's `run_at` to now (`UPDATE background_jobs SET run_at = now() WHERE kind = 'integration' AND idempotency_key = 'drain:<id>' AND status = 'queued'`) and wakes it. ### 6.5 Events feed

`GET /v1/events?after=<cursor>&types=` returns this org's `integration_events` with `seq > after`, ordered by `seq`, at most 200, bodies built by `ExternalPayloads` for the calling key.
- **Starting point.** Without `after`, the answer is `{items: [], next: <cursor>}` where the cursor sits just before the first event still inside the 2-minute hold (or at the newest event). That is how a new integration starts, and how a client recovers from `410`.
- The cursor is an opaque string wrapping the per-org `seq` and `EVENTS_EPOCH` (an `Env` value). Because `seq` is per org, it reveals nothing about other workspaces. An operator bumps the epoch after any database restore (section 11.1 item 13); a cursor from another epoch gets `410 cursor_expired`, because after a restore new events can reuse numbers a client has already passed.
- **2-minute hold, cut at a `seq` boundary.** The feed returns only events whose `seq` is below the lowest `seq` of any event created in the last 2 minutes. Cutting on `seq` keeps order and at-least-once delivery even if the server clock ever steps back; `created_at` is `clock_timestamp()` after the emit lock (section 6.1), so the 2 minutes are measured from when the event was really written, not from when its transaction started. Polling is every 1-5 minutes anyway.
- **`superseded`.** Bodies are built at read time. A `contact.stage_changed` carries `superseded: true` when **a later `contact.stage_changed` exists for the same candidate** (it may still be inside the hold). So only the newest stage event per candidate is actionable: decide, Undo, decide again gives one actionable event, not two. The reference docs say: act on a stage event only when `superseded` is `false`. With the hold, a decide-then-Undo (the in-app Undo lasts 8 seconds, FACT `apps/web/components/ui/toaster.tsx` line 78) reaches a poller as a superseded decision followed by its reversal, so a "not moving forward → send a rejection email" workflow does not fire.
- The contract: **at-least-once, ordered within your workspace, events at least 2 minutes old, 30-day window**. If events after `after` have been purged (`after < min(seq) - 1`), the answer is `410 cursor_expired` ("Events older than 30 days are gone. Call GET /v1/events without `after` to get the current cursor."), never a silent skip.
- Correctness rests on the per-org emit lock and on `seq` never going down (section 6.1). Merge-blocking tests: two concurrent emits in one org, the later one committed first, and a poller sees both, in order; and a quiet month (see the "Purge" test, section 11.1).
- Polling every 1-5 minutes is the expected use. An iPaaS on a slower schedule sees results later (R12).

- The country code is written without `+`, so the formula escaping never touches it. How Excel and Google Sheets show a 10-digit phone cell is unverified; check both before shipping, and check that the file re-imports through the existing CSV preview with no issues.

### 6.8 Queue changes (Core)

FACT about today's code (`JAVA/jobs/JobQueue.java`): 2 worker threads for every kind and tenant (lines 50-54); `runScope` drains one org until empty, 10 jobs per claim (116-134); `poll()` runs `runDue()` inline on Spring's scheduler thread (87-90); job rows are visible only inside their org (RLS), so finding work means one transaction per org (93-109).

Changes:
1. **Outbound lane.** Kind `integration` is claimed only by a separate 2-thread executor. Within the lane, a pass claims at most **one job per org**, round-robin over an in-memory set of orgs with due lane work. The set is fed by `wake()` and by the existing 30-second poll (the safety net). `ponytail:` in-memory set per replica; a due-orgs table past ~1k orgs. `email` and `document` behave exactly as today. The 60-second tick likewise visits only orgs in an in-memory set of orgs with a connection that has been active and is not disconnected (fed by connect, reconnect and disconnect, filled once at startup), instead of opening one transaction per active org every minute. Work that must reach every org (the daily purge) stays in the existing 5-minute loop, which already visits every active org.
2. **`Snooze(seconds)`.** A handler may return a snooze. `execute()` sets the same row back to `queued` with `run_at = now() + seconds`, gives back the attempt and calls `wake(scope, seconds)` the way the retry path does (FACT, `JAVA/jobs/JobQueue.java` line 159), so `Snooze(0)` page chaining does not wait for the 30-second poll. It serves page chaining, rate-limit pauses, the drain backoff and the stage-write hold.
3. **POLICY** `integration` `{5, 30}`. Handlers own their expected retries through `Snooze`; queue attempts only cover unexpected errors.
4. **Scheduler pool.** One thread per `@Scheduled` method: 3 in A2 (`JobQueue.poll`, the 5-minute loop, the `DocumentProcessor` sweep), 4 from Core (the 60-second tick). A test fails when the number of `@Scheduled` methods exceeds the configured pool size. **Ships in A2** (section 6.1).
5. **Unknown kinds** throw a clear error at `enqueue`.
6. `/health` reports backlog per kind.
7. **Connection pool check** in the A2 definition of done and again in Core: pool size ≥ 2 × (lane threads + legacy workers + 1 dial thread) + 1 for a token refresh held during an HTTP call + 1 for the inline sweep + headroom for the scheduler and web traffic (FACT: `underAdvisoryLock` holds one pooled connection while its work uses others, `Db.java` lines 97-115; pool default 10, `Env.java` line 88).

8. **Health and alerting.** Each background loop (the dial thread, the 5-minute loop, `JobQueue.poll`, and from Core the 60-second tick) records an in-memory `lastRunAt`; the dial thread catches `Throwable` per pass and keeps running. Two lag numbers are computed with the time they were computed: `oldestQueuedCallMinutes` (the oldest `due_at` among due bulk rows; A2) and `oldestUndeliveredMinutes` (the oldest event above any sending connection's `fanout_seq`; Core). Public `/health` keeps its readiness fields **except `jobsBacklog`**, and its `status` becomes `degraded` when any heartbeat is older than 3 times its interval or either lag is over 30 minutes; it stays HTTP 200, because the Compose healthcheck treats any non-2xx as unhealthy (FACT, `docker-compose.yml` lines 122-127). The numbers, `jobsBacklog` and the oldest pending provider delete go into one structured log line a minute, not onto the public route. FACT why: `/health` is `@Public` and Caddy routes it to the internet (`JAVA/platform/HealthController.java` lines 26-39, `docker/Caddyfile`), and platform-wide figures there would let anyone watch HRVoice's activity, which per-org `seq` was chosen to avoid. **Gate P adds one external uptime monitor** with a keyword check on `"status":"ok"`, wired to the founder's phone or email (FACT: ADR-006 lists "monitoring with alerting" as our obligation, `BRD's/10_ADRs/ADR-006-hosting-deployment.md`, Consequences; no alerting is configured in the repo, grep of compose files, `docker/` and `.github/`). `ponytail:` heartbeats, a log line and one keyword monitor, not a metrics backend; actuator endpoints are not exposed today (`application.yml`, `management.endpoints.web.exposure.exclude: "*"`).

Slice A2 needs items 4 and 7 and its half of item 8; the rest is Core.

## 7. Two-way action architecture

```
Integration       integration_connections row (org-scoped, RLS): sending principal, status, config, delivery health
   ▼
Connector         AtsPort adapter + ConnectorSpec: auth type, readable objects, declared actions
   ▼
Available actions spec.actions ∩ enabled in connection.config ∩ use case actions.integrations
   ▼
Automation        fixed rules in code, not a rule builder:
                    call.ended (a settled call, a fact)        → ADD_NOTE   (always on for a connected ATS)
                    a person's decision: reviewed / declined   → SET_STAGE  (opt-in, customer-mapped, level-triggered, from a baseline)
                    custom connection                          → events feed (webhooks later)
   ▼
Agent             the voice agent never calls an action. It receives only the compiled job, questions and knowledge
                  (CallContextCompiler) and produces facts. It knows nothing about any connector.
```

**Provider independence of the core agent.** FACT: data reaches a live call only once, at provisioning, and the live agent gets only `end_call`, `voicemail_detection` and `transfer_to_number` (`JAVA/engine/CallContextCompiler.java` lines 26-37, 220-237). A connector changes rows in `jobs` and `candidates`; the compiler reads those rows as today.

**Where the never-recommend rule is enforced (three places, all testable):**
1. **Content:** only `ExternalPayloads` builds outbound text, without any summary (section 6.2).
2. **Trigger:** `SET_STAGE` sends only the candidate's current `screening_status`, and only `reviewed` or `declined`. That value is set only by a person through the stage routes (FACT, the only Java write of `screening_status` is `JAVA/hiring/Jobs.java` line 264). API keys cannot change stages. A call outcome never moves an ATS status. Model output never selects or triggers an external write (FACT, `BRD's/11_PERMISSION_MATRIX.md` line 149).
3. **Target:** adapters expose only `addNote` and `setStage`; no generic field update; never a score, rating, scorecard or recommendation field.

**Stage write-back (from a baseline).** Off by default. The customer picks the target status for "Moved forward" and for "Not moving forward" from their live status list.

- **Baseline.** Only decisions made after write-back is on, or after a row was linked, are sent. When a link is created or adopted, `pushed_stage` = the candidate's current stage. When write-back is switched on or its status map changes, one UPDATE sets `pushed_stage` = current stage for all of the connection's links. Earlier decisions are never sent in bulk. (Sending earlier decisions on request is V2, if a pilot asks.)
- **Finding work:** the tick finds candidates with a live link (`remote_state` not `'deleted'`, so removed and anonymised people are never pushed) where the current stage is `reviewed`/`declined` and differs from `pushed_stage`, or where the current stage is `new`/`screening` while `pushed_stage` is `reviewed`/`declined`. It enqueues `push_stage` with key `stage:<candidateLinkId>`.
- **The handler:**
  1. **Hold.** If the candidate's last `contact.stage_changed` is less than 2 minutes old, `Snooze` for the remainder. The in-app Undo lasts 8 seconds (FACT, `apps/web/components/ui/toaster.tsx` line 78; Undo re-posts the previous stage with reason "Undone", `apps/web/app/jobs/[id]/candidates/page.tsx` lines 680-698).
  2. **Read the current stage.** If it equals `pushed_stage`, stop.
  3. **Forward** (`reviewed`/`declined`): re-read the application's ATS status. **If it already equals the mapped target** (for example our own write just before a crash, when `pushed_stage` was not yet recorded), record `pushed_stage` and `remote_status_seen` and stop: no note, no `setStage`. Otherwise, if it differs from `remote_status_seen` (someone changed it in the ATS), do not overwrite: add a note "Moved forward by Priya Sharma in HRVoice; status left unchanged because it was changed in Zoho Recruit". Otherwise call `setStage` with the comment "Moved forward by Priya Sharma in HRVoice", and **in the same transaction that sets `pushed_stage`, set `remote_status_seen` to the status we wrote**, so our own write is never later mistaken for a change made in the ATS. Either way set `pushed_stage`. The name is the decider's display name, or "a team member" (section 6.2).
  4. **Withdrawn** (`new`/`screening` after `reviewed`/`declined`): add a note "Decision withdrawn in HRVoice by Priya Sharma. Status in Zoho Recruit not changed." and set `pushed_stage` to the current stage. We do not try to restore the earlier ATS status: it cannot undo what the ATS already did (an email, an automation), and the 2-minute hold makes this case rare.
- Because the handler always reads current state, retries and reordering cannot leave the ATS on an older decision. Stage changes made through Nest are caught by the same comparison.

**Notes (one per call, a follow-up only if the result changed).** The drain writes one note per `call.ended` version, including unanswered calls ("HRVoice called on 3 Oct, 11:02: no answer"). The marker is `HRVoice ref <session prefix>.<hash prefix of the rendered note text>`; the adapter skips the write if that marker exists, so a new version that renders the same note writes nothing. A real follow-up note is titled "Updated result for the call on 3 Oct, 11:02".

```
HRVoice screening call · Sales executive · 3 Oct 2026, 11:02 · 6 min
Outcome: Call completed            (or: No answer / Reached voicemail / Picked up, didn't speak / Number not valid / Result unavailable)

What they said
- Notice period: 30 days
- Current location: Pune
- Expected salary: not answered

Recording, transcript and summary: <sign-in link to the candidate in HRVoice>
A person on your team decides who moves forward. HRVoice does not score or recommend.
HRVoice ref 3f2a9c1e.a41b
```

**Later in-call actions** (for example booking an interview slot) are **not** reachable today. The live voice agent gets only provider system tools, and the tool gate needs a member `Actor` (FACT, `JAVA/engine/CallContextCompiler.java` lines 220-237; `JAVA/runtime/Tools.java` lines 19-26, 245-253). That path would need: a provider webhook-tool endpoint on our API; a short-lived call-scoped token passed as a secret dynamic variable; a call principal kind; read-only tools with a timeout of 5 s or less and a spoken fallback. It stays Later. Our server would call the ATS through the connection; the model never would.

## 10. Multi-tenancy and identity

- Every new table: forced RLS on `organization_id = current_org_id()`; listed in `StructuralTest`; no BYPASSRLS; `Db` keeps "no method that disables row-level security" (FACT, `JAVA/platform/Db.java` line 33).
- Tenant is resolved only from server state: the API key hash (narrow SELECT-only lookup), the signed-in member's session (OAuth callback: the `state` hash is compared on that member's org's `connecting` row), or, in V2, an inbound webhook connection (order in section 11.1 item 8). Never from an `organization_id` or `job_id` in a payload.
- **Performance isolation:** the outbound lane with one job per org per pass, one drain per connection with its own backoff, the dial thread with one row per org per pass, and per-key rate windows (sections 6.1, 6.6, 6.8, 13.1).
- **Shared voice-provider capacity (slice A2).** Every workspace dials through one provider account and one outbound number (FACT: one `voiceApiKey` and one `voicePhoneNumberId` in `Env`, `JAVA/voice/HostedVoiceAdapter.java` lines 47-49, 253-256). The account has one concurrency limit for all tenants: FACT, "Free 4 concurrent calls; Starter 6; Creator 10; Pro 20; Scale 30; Business 40" (https://elevenlabs.io/pricing/agents), and calls over the limit "are rejected with an error, unless call queueing is enabled" (https://elevenlabs.io/docs/eleven-agents/guides/burst-pricing). Per-workspace caps do not bound the total, and forced RLS means no query can count live calls across workspaces. Three measures, all in A2:
  1. **A capacity refusal is not a dial.** The adapter returns `provider_busy` for an HTTP 429 from the dial request, **or** for a `success: false` body without a conversation id whose message matches `concurren|too_many|system_busy|capacity` (the provider documents both 429 messages, `too_many_concurrent_requests` and `system_busy`, as requests that were not processed; the outbound-call reference documents only a 422 and the `success`/`message` body; which shape an over-capacity dial really gets is unverified, section 17). `dialLocked` then deletes, in one transaction, the `voice_sessions` row it just inserted (`DELETE ... WHERE id = ? AND status = 'pending' AND external_conversation_id IS NULL RETURNING session_id`) and its `agent_sessions` row: no ledger row, no `call.started`. The application role may do this only through A2's RESTRICTIVE delete policy (section 2.3), so a call the provider accepted can never be deleted. If the delete matches no row, something else already changed the session; it is left as it is and logged. Then `dialLocked` writes the audit row `voice.session.provider_busy` with ids in metadata and raises `calls.provider_busy` ("All call lines are busy right now. Try again in a minute."). The candidate shows no failed call, the daily cap is unchanged, and a queued row goes back to `scheduled` at +60 s. Rows are deleted rather than kept under a new status, because a kept row would need an exclusion in `counts()`, `Jobs.callStatus` and `queue`, the Calls list and analytics. Any other refusal keeps today's handling.
  2. **A platform ceiling on bulk dials.** `VOICE_BULK_MAX_CONCURRENT` (default 2). The dial thread keeps, in memory, the live phone-call count it last read for each org in its bulk set (it reads it anyway, inside the claim transaction it opens per org per pass) and claims a bulk row only while the sum is below the ceiling. People's own Call clicks are not limited by it, so they keep the rest of the account's capacity. The founder sets it to the plan's concurrency minus the slots kept for clicks (proposed: half the plan). Orgs still take turns, so freed slots go round-robin. `ponytail:` per replica, and the count is at most one pass (15 s) old; the 429 handling above catches what it misses.
  3. **Burst stays off.** Burst pricing is "configured per agent" and charges extra calls "at double the standard rate" (same burst page). `agentBody` never enables it, and a test asserts the provisioned body has no burst setting; this is a decision recorded in ADR-010. Whether it is off by default is unverified (the page describes it as something you "toggle on").
- **Shared calling number.** Every workspace's calls come from the same number. A block or a wave of complaints against it would stop calling for every tenant at once. Recorded as R22 and in founder decision 10a.
- **Destination allowlist (slice 0).** `VOICE_DIAL_COUNTRY_CODES` (default `91`). `dialLocked`, the single dial choke point, refuses an E.164 number outside it with `calls.destination_not_allowed` (A2: the row is `skipped`); intake flags it too (section 6.6). FACT why: `PhoneNumbers.toE164` accepts any `+[1-9]\d{7,14}` (`JAVA/engine/PhoneNumbers.java` lines 8-20), and `TELEPHONY_OPEN_OUTBOUND` "Controls desk messaging — does not change dial mechanics" (`apps/api/src/config.ts` lines 190-198). A2 turns one click into up to 50 unattended dials a day per workspace, `/v1` lets a key add 2,000 rows a day, and sign-up creates a workspace at once; premium-rate or international numbers dialed on our shared account and number are a cost (toll-fraud) and reputation risk (R22). The gate P checklist limits the carrier's geo-permissions to the same list.

**API key principal: the key acts as its creator, re-checked on every request.** (FACT why not `Db.NIL`: `audit_events.actor_user_id` and `jobs.created_by_user_id` have foreign keys to `users`, `MIG/0000_initial_schema.sql` line 132, `MIG/0015_hiring_desk_foundation.sql` line 43; `AuditService` swallows failures, lines 56-59; `Actor` requires a membership.)

1. `AuthResolver`, only for handlers of the `/v1` controller (chosen by `AuthInterceptor` from the matched handler, never by a path prefix, section 6.6) with `Authorization: Bearer hv_...`: hash the key and read it through the narrow lookup. **The key is valid unless** it is revoked, it has expired, its connection is `disconnected`, or its creator is no longer an active member of an active workspace with an active user account (`membership(createdByUserId, organizationId)`). **`AuthResolver.membership` itself gains the last two conditions** (`users.status = 'active'`, `organizations.status = 'active'`), so sessions, keys and the A2 dial thread share one guard. FACT: today the session path checks `users.status` before calling `membership` (`JAVA/authz/AuthResolver.java` line 44), `membership` checks only the membership's status (lines 59-80), and `Organizations.validateMembership` also checks the workspace's status. **Nothing about delivery health, `needs_attention` or the connection's sending principal affects a key.**
2. Effective permissions = **key permissions ∩ the creator's live permissions**. Demoting the creator narrows the key on the next request.
3. `AuthContext` gains one nullable field, `apiKeyId`. `userId` is the creator, so every existing service, foreign key and audit path works unchanged. The key's `Actor` carries the synthetic `roleKey` `api_key` with `roleIsSystem = false`, so `Actor.isOwner()` is always false for a key (FACT: `isOwner` reads `roleKey`, `JAVA/authz/Actor.java` lines 25-26). `AuthInterceptor` adds `apiKeyId` to the metadata of `authz.denied` and `authz.sensitive_access`; Settings > Activity shows "via API key '<name>'" when `metadata.apiKeyId` is present, and the audit CSV gets an `api_key_id` column.
4. No synthetic user or membership row is created for keys. Owner-only checks are unreachable with a key, because keys only work on `/v1` and `isOwner()` is false. **Rule for ADR-010:** code reachable from `/v1` uses `Actor.permissions` only and never re-reads `role_permissions` by user id, which would return the creator's full rights instead of the intersection (FACT: one such re-read exists, outside `/v1`, `JAVA/runtime/AgentRuntime.java` lines 169-174). A grep test fixes the list of files allowed to read `role_permissions`. A key never supplies `decidedBy`: there is no stage route in `/v1`.
5. A key whose creator left shows "Needs attention: the person who created this key no longer has access. Create a new key."

**Workers** (sync, drain, the inline sweep, reconcile) run `inOrg(org, Db.NIL)` and pass **`null`** to `AuditService`, which stores NULL (FACT, `VoiceSessions.webhook` calls `audit.record(org, null, ...)`).

**The connection's sending principal** (`created_by_user_id`) matters only for connections that send (ATS notes and stage write-back; webhooks later). Its live permissions decide content (section 6.2). If that person leaves or loses `integrations.update`, the connection gets `needs_attention` with reason `principal_lost`, and sends stop until an admin presses "Take over" (audited). Pulls continue, and API keys are unaffected.

**The dial thread** (slice A2) rebuilds the clicking person's `Actor` from their live membership (the same guard: active user, active workspace) for each row. If they no longer hold `calls.initiate`, the row is skipped with a reason. It dials with the job's **current** agent, read at dial time; the row's `agent_id` is kept only because the column is NOT NULL, so relinking a job to another agent while calls are queued does not cancel them (FACT: `dialLocked` refuses when the passed agent differs from `jobs.agent_id`, `JAVA/voice/VoiceSessions.java` lines 401-404).

## 11. Security

### 11.1 MVP gates

1. **`Sealer`** (built in slice E or Webhooks, whichever ships first; nothing needs it earlier) generalised from `Notifications.seal`: AES-256-GCM, 12-byte random IV, keys from `INTEGRATIONS_KEYS` (`1:<base64>,2:<base64>`) and `INTEGRATIONS_KEY_CURRENT`, never derived from `BETTER_AUTH_SECRET` (FACT: rotating it already kills sealed mail, `apps/api-java/MIGRATION_STATUS.md` line 358). Output `k<version>.<base64>`, AAD = `organization_id:connection_id:secrets`. `Env` refuses to boot if the current version is not in the key list. A re-seal command (same pattern as the `--desk.reembed` CLI arguments, FACT `MIGRATION_STATUS.md` line 346) walks every org with `inOrg` and re-seals old versions; an old key is removed only after it reports zero rows left. A boot-time check of "every version still in use" is not possible: the rows are behind forced RLS and there is no bypass (FACT, `Db.java` line 33). A row sealed with a missing version opens as "reconnect needed". Do not reuse the plaintext `accounts.*_token` columns.
2. **API keys:**
   - format `hv_live_` + 32 random bytes; SHA-256 stored; shown once; UI prefix `hv_live_` + 6 characters (the fixed prefix lets a customer's own secret scanner match leaked keys; a checksum suffix waits until we join a scanning partner programme, V2);
   - presets, exactly:
     - "Send candidates in" (default): `jobs.read`, `jobs.create`, `candidates.create`, `candidates.update`; `candidates.delete` only through an explicit "May remove people" checkbox, so a leaked default key cannot start erasures. It cannot read the feed or results (both need `candidates.export`), and `PUT` returns only ids and issues, so a leaked inbound key cannot page the workspace back out. Pending removals show on the status card with their date;
     - "Read results": `jobs.read`, `candidates.read`, `calls.read_transcript`, `candidates.export`;
     - "With contact details": "Read results" plus `candidates.read_pii`;
     - "AI assistant (read-only)" (only if the MCP pilot happens): `jobs.read`, `candidates.read`, `candidates.export` (names and decisions leave the workspace), expiry required, 90 days or less;
   - never `users.*`, `roles.*`, `integrations.*`, `organization.*`, `billing.*`;
   - effective permissions intersected with the creator's live permissions (section 10); validity rule in section 10;
   - revocable; expiry one year by default, "No expiry" as an explicit choice; `last_used_at`; creating one needs `integrations.create`; two keys may be live during rotation;
   - header only, `/v1` only. Disconnecting the `custom` connection revokes its keys in the same transaction.
3. **Who may connect what:** connect, edit, Retry and disconnect need `integrations.create/update/delete` (Owner, Administrator). Recruiters (who hold only `integrations.read`) see the status and "Ask a workspace admin". Content leaves only under the one export rule (section 6.2).

1. 4. What goes into the ATS note? **Default now: outcome, answers and a sign-in link, no summary**, because the stored summary is the voice provider's, not ours. A summary outside HRVoice needs our own summary first (V2). (D9)
5. Is it acceptable that ATS-linked contact fields are read-only in HRVoice? (D10)
6. May a stage change ever come from another system rather than a named person in HRVoice? (D11)
7. May "Not moving forward" set a reject status in the ATS (which may email the candidate), given the 2-minute hold and that earlier decisions are never sent? (D12)
8. May the customer's own system name ("Zoho Recruit") appear in the UI?
9. Retention period for pulled-but-never-called candidates and transcripts; the grace period before anonymising people deleted in the ATS or through `/v1`; confirmation that we act as a DPDP processor; DPA. The provider-side retention on hosted agents follows the retention period (section 11.1 item 10). How long database backups keep erased data. And: should "Remove this person" stop that phone number being called for **every** job in the workspace (a do-not-call list, section 13.2), or only stop that application coming back, as today? (D17)
10. Automatic calling of imported candidates: yes or no, and under what consent, hours and DND rules? (needs legal advice)
    - **10a.** Ship "Call selected (N)": one person's confirmed click queues calls for the chosen people within calling hours, each dialed at most once. A legal check is needed on whether a queued batch counts as an "auto-dialer" under TCCCPR (unverified). Batches for different jobs run side by side (one hosted agent per job); one batch uses at most 2 of the 3 call slots, so a person's own Call still works. **Capacity is shared across workspaces:** every workspace dials through one voice-provider account and one calling number, so calls may wait behind other workspaces' batches. ## 18. ADR-010 contents (to lift verbatim)

Every rule below is stated, with its evidence, elsewhere in this document. This list collects them so that ADR-010 and the build sheets cannot miss a rule that appears only once inside a paragraph (Round 5 EIA-6).

**Gates**

1. Gate P: Java serves production before any slice ships there; gate P includes one external uptime monitor and carrier geo-permissions limited to the dial allowlist (sections 6.8, 13.1).
2. Core is built only together with E or Dev, after ADR-010 is written, and goes live only once Nest is no longer routed in production (section 13.1).
3. The retention, erasure and DPDP items go live before the first external connection (section 11.1 item 10).
4. A2 needs founder decision 10a, including the provider plan and the legal check (section 16).

**Tenancy and identity**

5. Every new table: forced RLS on `organization_id = current_org_id()`, listed in `StructuralTest`; no bypass; the tenant comes only from server state (section 10).
6. API keys work only on `/v1` handlers, only as a bearer header, only on `API_PUBLIC_HOST`; the principal type is chosen by the matched handler, never by a path; cookies are ignored there and keys everywhere else. Effective permissions = key ∩ the creator's live permissions; `AuthResolver.membership` checks the user, the workspace and the membership (sections 6.6, 10).
7. Code reachable from `/v1` never re-reads `role_permissions`; a grep test fixes the files allowed to (section 10).
8. Workers run `inOrg(org, Db.NIL)` and audit with a NULL actor (section 10).

**Product rule**

9. Only `ExternalPayloads` builds outbound bodies: no summary; no score, coverage, rank or recommendation; answers only to the job's own questions (`criteriaSource = 'job'`), scrubbed and as plain text; public decision values; display names, never emails; one export rule (section 6.2).
10. Only a person's decision moves an ATS status: opt-in, after a 2-minute hold, from a baseline, reading current state, checking "already at target" first (section 7).

**Events**

11. Every emitting transaction takes the org events lock as its first statement. Lock order: the events lock, then the job row, then candidate rows. The sweep scans without the lock and takes it only to emit (section 6.1).
12. `seq` is per org and `created_at = clock_timestamp()` after the lock; the purge cuts below a `seq` boundary and always keeps the newest event; cursors only move forward (`greatest()`); feed cursors carry `EVENTS_EPOCH` (sections 6.1, 6.5).
13. A call is settled when it has a failure reason or a transcript, or 90 minutes have passed; one `CallOutcomes.outcome` serves the app and every body; dedupe is a compare-and-set on the call row (section 6.1).

**Calls**

14. Every dial goes through `dialLocked`: budget, caps, destination allowlist, the closed-in-ATS block, one live call per person (section 10).
15. A dial is placed, not placed or may have been placed, decided by the transport; only a never-placed session may be deleted, and only through the RESTRICTIVE delete policy (sections 2.3, 6.1, 10).
16. A bulk row is dialed at most once; every status change sets `updated_at`; the dial uses the job's current agent; the per-org caps and the platform bulk ceiling both apply; burst stays off; no dashboard batch calls on the production account (sections 10, 13.1).
17. A dial whose knowledge retrieval failed is refused, never re-synced (section 13.1).
18. Phone calls use the `job:<id>` slot, browser tests the `test` slot; idle stale job agents are deleted at the provider and their rows kept (sections 2.3, 11.1 item 10).

**Background work**

19. The 5-minute loop always runs: database work first, reconcile at most 40 s, provider deletes at least 15 s; only the provider steps follow `ELEVENLABS_ENABLED`. One scheduler thread per `@Scheduled` method, checked by a test (sections 6.1, 6.8).
20. Each loop records a heartbeat; public `/health` says `ok` or `degraded` and shows nothing cross-tenant; an external monitor watches it (section 6.8 item 8).
21. `AUTOMATION_PAUSED` stops the dial thread, the tick, the lane and the provider steps (section 11.1 item 13).

**Data protection**

22. One erasure path. `apply` returns early for erased calls. An anonymised ATS link keeps only its suppression hash. Connection rows are never deleted while the workspace exists. Every person-level erasure and workspace deletion is also recorded outside Postgres and re-applied after a restore (sections 2.3, 11.1 items 10 and 13).
23. Audit rows store route templates, never query strings; audit rows are kept (no UPDATE on `audit_events`), and the DPA says so (section 11.1 items 7 and 10).
24. Before Core, migrations only add things Nest ignores (R10).
25. The provider plan's concurrency is a capacity input, and the shared calling number is a shared risk (section 10, R22).
