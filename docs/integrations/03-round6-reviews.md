### review:v6:integration: block
1. [major] (A2 shared capacity on the default India (Exotel) route) The rule "a capacity refusal is not a dial" (section 1 item 7, section 10 measure 1, section 18 rule 15) only covers the voice provider's own concurrency limit (HTTP 429, or a success:false body matching concurren|too_many|system_busy|capacity). The route production uses by default is Exotel, and Exotel has its own channel cap. When Exotel refuses, the refusal is classified carrier_blocked. Under the A2 error table that is "anything else": the session is marked failed, it counts toward the workspace's daily cap of 50, and the queued row becomes done or skipped and is never dialed again. So when Exotel's channels are full, or its credentials are wrong, a batch fails row by row. Each row shows a failed call, the daily cap runs out, and oldestQueuedCallMinutes never alerts because the rows are being processed. The channels are shared, so one workspace's manual clicks plus another workspace's batch can burn a third workspace's queue. The capacity formula in decision 10a and the A2 live check use only the voice provider's plan concurrency.
   evidence: FACT, docker-compose.yml line 101: `ELEVENLABS_OUTBOUND_PROVIDER: ${ELEVENLABS_OUTBOUND_PROVIDER:-india}`; .env.example line 144 sets `india`. FACT, apps/api-java/src/main/java/desk/voice/HostedVoiceAdapter.java (dial): `india` routes to /v1/convai/exotel/outbound-call. FACT, apps/api-java/src/main/java/desk/engine/CallOutcomes.java: CARRIER_BLOCK matches `exotel_connect_failed|failed_dependency|connect api returned|upstream_service_error`, so fromDialFailure returns `carrier_blocked`. FACT, https://elevenlabs.io/docs/eleven-agents/phone-numbers/telephony/exotel: ask Exotel support to "Provision the number of channels (concurrent calls) you need. This is the cap on simultaneous Voicebot calls Exotel will let your account run". Its troubleshooting entry for `exotel_connect_failed` reads "ElevenLabs received a non-200 response from Exotel's Connect API", which means Exotel did not dial, so the call was not placed. Unverified: which exact body a full Exotel account returns.
   proposed: In section 10 and the A2 error table, add a third class: an account-level refusal that was not placed. That covers carrier_blocked or line_not_connected returned by the dial with no conversation id, and any `exotel_connect_failed` body. For this class: (1) delete the two session rows through the existing vs_delete_unplaced policy, so the daily cap is not used; (2) set this row and the job's other open bulk rows to `scheduled` at +5 min with reason `bulk:line_problem`, the same handling as provision_failed, so oldestQueuedCallMinutes alerts after 30 minutes; (3) for a manual click, show "The calling line refused this call" with no failed session. In decision 10a and the capacity formula, set VOICE_BULK_MAX_CONCURRENT to at most min(provider plan concurrency, Exotel channels) minus the slots kept for clicks. Extend the A2 live check so it fills the Exotel channels and logs the real refusal body. Add a FakeVoice test: an `exotel_connect_failed` refusal leaves no session, uses no daily-cap slot, and re-queues the row.
2. [minor] (Idle stale job-agent deletion races a concurrent dial) The provider step deletes a job slot's hosted agent once it has checked that the slot is idle (no pending or active session, no open bulk row). It does not take the agent-version advisory lock that provisionLocked and dialLocked hold. A manual Call click for that job can provision or reuse the agent between the idle check and deleteAgent. The dial then goes to a deleted agent, or the loop's later UPDATE blanks the external_agent_id that the click just wrote. The most likely trigger is a knowledge-document delete, which marks every idle job slot stale at once while recruiters keep clicking Call.
   evidence: FACT, JAVA/voice/VoiceSessions.java: startOutbound runs `db.underAdvisoryLock(versionLock(a.versionId()), () -> dialLocked(...))`, and provisionLocked reads and upserts the slot on every dial. Draft section 11.1 item 10 ("idle job agents") names no lock. Job status does not gate dialing (02-resolutions, AM-2, round 1), so a closed job's slot can still be dialed.
   proposed: Run each idle-agent delete under `underAdvisoryLock(versionLock(agent_version_id))`. Re-check idleness under the lock, call deleteAgent, then blank the row with a compare-and-set (`WHERE external_agent_id = :old`). If the lock is busy, skip the item until the next run.
3. [minor] (The outcome sweep's compare-and-set ignores erasure) The sweep reads and hashes rows without the events lock and then compare-and-sets under it. The CAS checks only result_emitted_hash. If an erasure commits between the scan and the CAS, the sweep emits call.ended for a call that is already erased. Later bodies show no content, so nothing leaks, but the event and any delivery attempt are noise, and the rule "the outcome sweep skips erased calls" is not true.
   evidence: Draft section 6.1: `UPDATE voice_sessions SET result_emitted_hash = <hash> ... WHERE id = ? AND result_emitted_hash IS DISTINCT FROM <hash>`. Erasure never takes the events lock (section 6.1 lock order).
   proposed: Add `AND content_erased_at IS NULL` to the compare-and-set.
4. [minor] (Jobs created through /v1 cannot be called until someone opens each one) `PUT /v1/jobs/by-external` creates a job with a title and description only. A job with no agent cannot be phoned, and "Call selected" is disabled for it. The Zoho flow pre-selects the agent when the workspace has exactly one published agent. The /v1 path has no such step, and the reference docs do not say that a person must link an agent first. For a custom system that creates jobs automatically, the automatic flow stops without warning at "cannot call".
   evidence: FACT, apps/api-java/src/main/java/desk/hiring/HiringController.java line 352 (outbound-call needs the job's agent). Draft section 12.2 step 7 pre-selects the agent for Zoho only. Section 6.6 has no agent field and no default.
   proposed: When the workspace has exactly one published agent, link it to /v1-created jobs, the same rule as the Zoho step 7. In every case, return `needsSetup: ["agent", "questions"]` in the PUT response and say so in the reference docs.

   evidence: FACT: `apps/api-java/src/main/resources/usecases/hiring.json` line 86: "About the role ({{workUnitTitle}}) ... FACT: `JAVA/rag/ContextPacker.java` lines 14-23: OPEN = "<<<UNTRUSTED_DATA", CLOSE = "END_UNTRUSTED_DATA>>>", and sanitize() replaces only those two strings. FACT: the draft's section 6.6 `PUT /v1/jobs/by-external` and section 12.2 step 3 copy the title and the full JD from machine sources. FACT: resume text reaches no LLM (only `hiring/Candidates.java` and `HiringController.java` reference it), so the JD and the title are the only inbound fields that reach the live agent.
   proposed: Add these to slice E/Dev (or slice 0, since the fix is tiny): (1) render the role block with the same markers that `sanitize` neutralises, using `ContextPacker.fence("role", brief)`, or make `sanitize` also neutralise `<<<ROLE` / `ROLE>>>`; (2) on every path, strip new lines and fence markers from the title, and move it inside the fenced block or reduce it to a single-line label; (3) add one merge-blocking test: a JD containing `ROLE>>>` followed by an instruction, and a title containing a new line and an instruction, both stay inside the fence in the compiled prompt. Also state in section 11.1 item 9 that untrusted JD text is fenced and that the title is cleaned. Changing the prompt text changes the context hash, so every hosted agent re-syncs once on its next dial. Note that in the build sheet.

### review:v6:enterprise: block
1. [major] (A2 idle stale job-agent deletion can destroy recordings and break reconcile) v6 adds a step to the 5-minute loop that deletes, at the voice provider, any idle job agent that is stale. Stale means an old agent version, a closed job, or any company document deleted since the agent's last dial. The draft treats this as harmless because the deployment row is kept. But recordings are not stored by HRVoice. They are streamed on demand from the provider by conversation id, and background reconcile fetches conversations up to 60 minutes after a call ends. The provider documents a DELETE endpoint for agents, but not what happens to that agent's conversations, audio or per-agent retention setting after the agent is deleted (unverified). If deleting an agent removes or orphans its conversations, then publishing a new agent version, or deleting one company document, would within 5 minutes make every idle job agent of that org stale and delete it. That would wipe the recordings and transcripts of every past call on those jobs. It would also break reconcile for recently ended calls whose webhook was lost ("idle" only excludes pending or active sessions). This loss cannot be undone and hits the product's core promise ("transcript and recording one click away"). The only test uses FakeVoice, which cannot show this behaviour. The A2 definition of done makes the test mandatory, so implementation would ship it.
   evidence: FACT: recordings are fetched live as `GET /v1/convai/conversations/{id}/audio` (`apps/api-java/src/main/java/desk/voice/HostedVoiceAdapter.java` lines 189-193) and are not stored (backend map §8.2). FACT: the provider's Delete-agent reference lists only the agent_id path parameter and a 422 error, and says nothing about conversations (https://elevenlabs.io/docs/api-reference/agents/delete, fetched 2026-10-03). FACT: retention is configured per agent, and shortening it with "apply to existing data" may result in immediate deletion (https://elevenlabs.io/docs/eleven-agents/customization/privacy/retention). Draft v6 §11.1 item 10 ("idle job agents (A2)"), §2.3 `voice_provider_deployments` row, §13.1 A2 definition of done ("idle-agent ... tests"), §18 item 18.
   proposed: Take idle-agent deletion out of A2. To meet SA-4's concern without deleting anything: when a company document is deleted, the provider step of the 5-minute loop re-syncs idle `job:` slots in place, through the existing provision/update path. The new compiled context no longer contains the deleted excerpt, and the agent id and its conversations stay. Old-version and closed-job agents are left alone until workspace deletion, where `deleteAgent` runs only after every conversation has been deleted (as v6 already orders it). Add one step to the A2 supervised live check on a test account: place a call, delete its agent, then GET the conversation and its audio. Allow stale-agent deletion (V2) only if both still work. Update §2.3, §11.1 item 10, §13.1 (A2 definition of done), §17 and §18 item 18 to match.
2. [minor] (Restore re-apply relies on object-storage operations that do not exist) v6 records each erasure as `erasures/<org>/<candidateId>` in the "existing object storage" and has `--desk.reapply-erasures` enumerate these records. `ObjectStorage` has only `put` and `get`. It has no list and no delete. Its keys are always built as `<org>/<key>`, so the stated layout cannot be produced. The restore command therefore needs a new list operation (ListObjectsV2 by prefix per org, iterating the restored orgs), and the key layout must be `<org>/erasures/<candidateId>`. In dev and test the backend is local disk on the same host, so the records do not survive a host loss there. Production uses R2 (external), which is fine.
   evidence: FACT: `apps/api-java/src/main/java/desk/knowledge/ObjectStorage.java` lines 63-73 (`objectKey` = org + "/" + key) and lines 81-99 (only put and get). FACT: `docker-compose.prod.yml` lines 34-40 set `STORAGE_BACKEND: s3` (R2 per ADR-006 line 152).
   proposed: In §11.1 item 13: use the key `<org>/erasures/<candidateId>` (and `<org>/erasures/workspace`). Add `ObjectStorage.list(org, prefix)` to Core's scope, and make the restore command iterate the organizations in the restored database. State that the guarantee assumes the S3/R2 backend.
3. [minor] (Delete policy protects 'not yet recorded as placed', not 'never placed') The RESTRICTIVE policy matches any `pending` session with no `external_conversation_id`. That also covers a dial in flight, and a call the provider accepted where the follow-up `UPDATE ... set status='active', external_conversation_id` did not commit (crash or DB error after `voice.dial` returned). The draft says the policy guarantees that "a call the provider accepted can never be deleted". It does not: only the code path (delete by its own id, after a definite refusal) gives that guarantee.
