## 1. The decisions on one page

1. **The goal is a sync problem, not an AI problem.** "Connect once, data flows in, the agent works, results flow back" needs a machine identity, provenance (external ids), a durable record of what is still to be sent, a way to send it, and one adapter per named system. MCP does not provide delivery, retries or sync (FACT, https://modelcontextprotocol.io/specification/2026-07-28/changelog: "a broken response stream loses the in-flight request").
2. **Everything lives inside `apps/api-java`, on the same Postgres.** No new service, broker, Redis, Kafka or workflow engine. Reuse `Db.inOrg` and forced RLS, the narrow-lookup pattern, `background_jobs`, `AuthInterceptor` with per-field PII redaction, `AuditService`, `AdviceGuard` and the CSV-import validation (FACT, backend map §2, §3, §5, §6.4, §10).
3. **Order of work:** gate P → prerequisites (0) → results CSV export (A) → then, **only when a pilot confirms which path it will use**, the integration core plus either the named connector (E, Zoho Recruit by default) or the developer surface (Dev: API keys, `/v1`, events feed). Webhooks only if a pilot needs push. Founder decision 1 picks the branch. For a pilot that keeps candidates in Excel or Google Sheets and has no developer, the MVP is CSV in and CSV out, so "connect once" is **not** met for that customer; the follow-up is a Google Sheet connection (section 13.2). **None of it reaches customers until the Java API serves production** (gate P): FACT, production builds and routes only the Nest API (`Dockerfile` line 61 `CMD ["node", "apps/api/dist/main.js"]`; `docker/Caddyfile`). Separately, two risks that exist today whatever happens to integrations are recorded as small separate items, not designed here (section 13.1): item G, self-serve phone calling on the shared number, and item W, data retention (how long recordings, transcripts and people are kept, for every workspace), workspace deletion leaving provider copies, and a database restore bringing back erased people.
4. **Data flows one way per field.** Jobs and candidate contact details flow **in**; call results and human decisions flow **out**. For ATS-linked rows the ATS owns contact fields, the server enforces that, and a correction made in the ATS reaches HRVoice at the next pull (section 5).
5. **The product rule holds at the boundary.** Only facts and decisions a named person made leave HRVoice: never `fitPercent`, a coverage percentage, a score, a rank, "qualified", or a stage the system chose. The stored call summary is written by the voice provider, so **no summary leaves HRVoice** until we write our own (founder decision 4). One serializer builds every outbound body and is tested for this.
6. **Results flow back even if nobody opens HRVoice.** In an org with a live connection, a background job fetches results whose provider webhook was lost. Every phone call the voice provider accepted (it has a conversation id) that ends after the connection exists produces one ATS note when the person came from the connected ATS (a live link; E), or one `call.ended` for every call in the workspace (Dev), unanswered calls included. People added by hand on a linked job, and people no longer visible in the ATS, stay inside HRVoice (round 9 IA-6). A dial that never reached the provider stays inside HRVoice. If no result can be fetched, the customer gets "result unavailable" instead of silence.
7. **Calls start from a person, as today:** one Call click for one candidate, through the existing route and guards. Calling many people with one click is a separate design that is not approved (`later-bulk-calling.md`). Fully automatic calling of imported candidates waits for a written founder decision on consent, calling hours and DND (FACT, `apps/api-java/MIGRATION_STATUS.md` line 373).
8. **Outbound problems never stop inbound data, and one failing item never stops the others**, an unexpected error included (round 11 BE-1). API keys, intake and the events feed do not depend on whether a customer's ATS write is healthy; each outbound item retries on its own schedule.
9. **MCP:** never inside a live call; never as the sync channel; our own read-only MCP server later, when a paying customer asks.

The honest MVP loop is therefore: **in automatically (once a pilot's system is known), one Call click per person, out automatically.** The founder's "our agents perform the workflow" is met for data in and results out, not for starting calls (R25). Founder decision 10b asks whether that is acceptable for the first pilots at their daily volume, before any pilot is quoted a date.

## 3. Connector abstraction

**RECOMMENDATION.** A connector is one Spring bean implementing `AtsPort`, plus a static `ConnectorSpec`. No plugin loader and no DSL: adapters are registered in a map by key, the same way `JobQueue` handlers register by kind (FACT, `JAVA/notify/Notifications.java` line 49, `JAVA/knowledge/DocumentProcessor.java` line 55).

```java
// Sketch only. Not code to commit.
record ConnectorSpec(String key, String displayName, Auth auth, List<String> scopes,
                     Set<Reads> reads, Set<Action> actions, Budget budget) {}

enum Action {
  ADD_NOTE,   // trigger: a settled call. Content from ExternalPayloads only.
  SET_STAGE   // trigger: a person's decision, read at send time. Never a call outcome, never a model.
}

interface AtsPort {
  ConnectorSpec spec();
  Page<ExternalJob>         listJobs(Conn c, String cursor);
  Page<ExternalApplication> listApplications(Conn c, Instant modifiedSince, String cursor);  // incremental pull, all linked jobs
  Page<String>              listChangedParents(Conn c, Instant modifiedSince, String cursor); // Zoho: Candidates modified in the window (round 10 IA-1)
  Page<ExternalApplication> listApplicationsForJob(Conn c, String jobRef, String cursor);  // nightly complete listing, only if spike (a) finds one
  ExternalApplication       getApplication(Conn c, String applicationRef);   // re-read after a parent change (E1); live status for the stage handler (E2)
  List<ExternalStage>       listStages(Conn c, String jobRef);              // read live; stages get renamed
  List<String>              noteMarkers(Conn c, ExternalApplication app);  // Zoho: the parent Candidate's notes
  void addNote(Conn c, ExternalApplication app, String text, String marker); // Zoho: written to the parent Candidate record
  void setStage(Conn c, ExternalApplication app, String stageRef, String comment);
  // Typed errors: RateLimited(retryAfter), AuthRevoked, NotFound, Rejected(fieldErrors), Transient
```

Only what can leave is hashed (as v6): the summary never leaves, so a summary filled later makes no new version. Whether the transcript has a user turn is left out of the hash: it is fixed once the transcript arrives, which the hash already sees (`ponytail:` a transcript rewritten later with a different speaker mix is not re-sent). Then, for each connection with a `pending` row whose `next_attempt_at <= now()`, not inside `rate_limited_until` and with its preconditions met, the tick enqueues `send:<connectionId>`, **only after that org's transaction has committed** (round 10 BE-4; FACT: `enqueue` commits in its own transaction, `JAVA/jobs/JobQueue.java` lines 66-75, `JAVA/platform/Db.java` lines 22-49). `ponytail:` rehashes up to 7 days of linked calls a minute per connected org; the upgrade is a dirty flag set by `apply`.

*Sending* (`send:<connectionId>`, on the lane): reload the connection and stop if it is `disconnected` or its sending principal is not live (section 10). Take up to 20 due rows ordered by `next_attempt_at`, **joined so that only rows whose link is live and, for notes, whose call has `content_erased_at IS NULL` are taken** (round 8 EIA-1, BE-1: a row on a `missing` link that was skipped kept its place at the front, so 20 such rows could hold up every other note and spend the customer's Zoho credits on marker reads). A row on a link that is not live waits as it is: it is sent if the link comes back, and expires on the tick otherwise. For each row taken:
1. **Only if the row's previous attempt ended uncertain** (its `last_error_code` records a timeout or 5xx after the request was sent), list the Candidate's note markers (vendor HTTP). A refused or failed marker read does not stop the write (round 10 CR-4).
2. **Then, in one short read immediately before the write** (round 7 BE-6), re-read the row, its call, its link **and the connection** (round 11 BE-5: if the connection is now `disconnected` or has lost its token or sending principal, the run stops here), and build the note with `ExternalPayloads` for the sending principal: if the call is erased (`content_erased_at` set), the link is no longer live, or the row is gone, skip it (the erasure path deletes the person's rows; this covers an erasure committed after discovery, round 6 IA-3 / BE-2). The marker carries the rendered note's hash prefix; if markers were listed and it is among them, write nothing; otherwise `addNote`. A removal that commits during the `addNote` call itself cannot be stopped without holding a lock across vendor HTTP; the DPA and the removal runbook say that a send already in progress can finish within seconds of a removal.
3. **Success** (or the marker existed): `UPDATE ... SET status = 'sent', sent_at = now(), attempts = 0, last_error_code = NULL WHERE id = ? AND content_hash = :hashReadInStep2`. If the hash moved meanwhile, the row stays `pending` and the next run sends the newer version once, as an "Updated result" note. The connection's `consecutive_failures` resets and `last_success_at` is set.
4. **Permanent refusal** (`Rejected`, `NotFound`, other 4xx except 408 and 429): the row becomes `failed` with its error code, **as a compare-and-set on the hash read in step 2** (round 11 BE-6: if discovery re-hashed the row meanwhile, it stays `pending` and the next run sends the newer version), and the run carries on with the next row. Card: "1 call result couldn't be sent to Zoho Recruit. Open it in HRVoice." A note refused as `NotFound` because a merge in Zoho moved the person to another Candidate record goes back to `pending` by itself when a pull rewrites `external_parent_id` (section 5; round 10 EIA-3), so no admin has to press Retry.
5. **Rate limited:** set `rate_limited_until` and stop.
6. **Transient** (timeout, 408, 5xx, `Transient`), with the same compare-and-set on the hash: `attempts + 1`, `last_error_code` records it (so the next attempt lists markers first, step 1), `next_attempt_at = now() + least(1 hour, 1 minute × 2^attempts)`; the connection's `consecutive_failures + 1` (`failing_since` on the first; one email to admins at the third: "Couldn't send since 10:40"); **the run stops**, because the vendor is probably in trouble. Rows are taken in `next_attempt_at` order, so a row that always fails moves behind the others and never holds them up: no probe is needed.
7. **`AuthRevoked`:** `needs_attention` (`consent_revoked`) and stop.
8. **Expiry runs on the tick**, as a database step, so it also reaches rows the sender no longer takes. It first **deletes** rows whose call has `content_erased_at` set or whose person's link on that connection is `deleted` (round 10 BE-2: a discovery statement that began before an erasure committed can insert such a row). Then a note row still `pending` 7 days after its call ended, or a stage row still `pending` 7 days after the decision (`candidates.updated_at`; round 7 IA-2, UX-1), becomes `failed` with `expired`; the card says "N call results from before 3 Nov couldn't be sent. Open them in HRVoice." or "N decisions couldn't be set in Zoho Recruit. Set them there by hand." Nothing disappears silently.
9. **Budget:** 20 rows or 120 seconds, far inside the queue's 900-second lease (FACT, `JobQueue.java` line 39); the next tick re-enqueues if rows are still due. The handler never throws for a delivery failure, so queue attempts are spent only on bugs.
10. **An unexpected exception for one row** (a mapping bug, `ExternalPayloads` failing on an odd answer object) is caught for that row and treated as Transient with `last_error_code = 'internal'`: the row backs off and moves behind the others, the error is logged by class, and the run goes on (round 11 BE-1). Without this, the same row would stay first in line on every run.

Consequences:
- **One note per call** normally; a follow-up note ("Updated result for the call on 3 Oct, 11:02") only when the rendered note changed.
- **Unanswered, failed and silent calls** the provider accepted get a note with their outcome.
- **No backlog on first connect**: the floor is `connected_at`.
- **Disconnect and reconnect** (round 7 EIA-5): discovery skips a `disconnected` connection, and a reconnect moves `connected_at`, so calls that ended while disconnected get no note. - **No order is promised between notes**; each note is about one call (`02-resolutions.md` R3.5: "Strict order is not needed for notes (each note is about one call)").
- **Nest-written results are caught too**, because discovery reads the database.

### 6.5 Events feed and event log (Dev slice only)

The ordered log exists only for the feed, so it ships only with the developer surface. Rules as already agreed (v6 §6.1 and §6.5), restated:

- **Emitting `call.ended`.** No use-case gate (section 6.1). In an org with a `custom` connection that has `connected_at` set and is not disconnected, the tick selects and hashes settled calls since that `connected_at` (within 7 days, `content_erased_at IS NULL`) **without** the events lock; only if a row's hash differs does it take the lock and run `UPDATE voice_sessions SET result_emitted_hash = :h, result_version = result_version + 1 WHERE id = ? AND result_emitted_hash IS DISTINCT FROM :h AND content_erased_at IS NULL RETURNING result_version` (the last condition is round 6's IA-3 / BE-2 fix: an erasure committed between scan and update emits nothing), then `Events.emit(sql, 'call.ended', {version})`.
- **Stage outbox.** In such an org, `Jobs.updateStatuses` takes the org events lock **as its first statement**, before `loadJob` locks the job row, and emits `contact.stage_changed` with `{from, to, decidedByUserId}` inside the existing `if (!previous.equals(...))` branch (FACT: the job row is locked first and this is the only Java writer of `screening_status`, `JAVA/hiring/Jobs.java` lines 255-264; `HiringController.java` lines 373, 386). Orgs without a feed take no events lock, so a recruiter's decision in an E-only workspace never waits on it.
- **Lock and `seq`.** `pg_advisory_xact_lock(hashtextextended('events:' || org, 0))` first in every emitting transaction; `Events.emit` reads `coalesce(max(seq), 0) + 1` and inserts with `created_at = clock_timestamp()` (FACT, https://www.postgresql.org/docs/current/functions-datetime.html); the 15-second `statement_timeout` maps to `ApiError.conflict("events.busy", ...)` as `Db.underAdvisoryLock` already does (FACT, `JAVA/platform/Db.java` lines 103-115). Lock order: the events lock, then the job row, then candidate rows; the sweep takes the events lock, then `voice_sessions` rows. Every transaction is READ COMMITTED (FACT: `Db` sets no isolation level), which the "lock, then read `max(seq)`" rule relies on.
- **Purge.** Once a day per org, from the 5-minute loop's database step: boundary `b = coalesce((select min(seq) ... where created_at >= now() - interval '30 days'), (select max(seq) ...))`, then `DELETE ... WHERE seq < b`. **The `max(seq)` fallback keeps the org's newest event, so `max(seq)` never goes down** and a quiet month cannot reuse numbers a client has passed.
- **Feed** `GET /v1/events?after=<cursor>&types=`: this org's events with `seq > after`, ordered, at most 200, bodies built at read time by `ExternalPayloads` for the calling key. Without `after`: `{items: [], next: <cursor>}` positioned before the hold. The cursor wraps the per-org `seq` and `EVENTS_EPOCH`; a cursor from another epoch gets `410`. **`410 cursor_expired` is defined against the oldest retained `seq`:** if `after < min(seq) - 1`, events after the cursor were purged, and the client is told to restart without `after`; never a silent skip.
- **2-minute hold, cut at a `seq` boundary:** only events whose `seq` is below the lowest `seq` created in the last 2 minutes are returned.
- **`superseded`:** a `contact.stage_changed` carries `superseded: true` when a later stage event exists for the same candidate, so decide, Undo, decide again yields one actionable event. The docs say: act on a stage event only when `superseded` is `false`.
- Contract: at-least-once, ordered within the workspace, events at least 2 minutes old, 30-day window.

## 7. Two-way action architecture

```
Integration       integration_connections row (org-scoped, RLS): sending principal, status, config, delivery health
   ▼
Connector         AtsPort adapter + ConnectorSpec: auth type, readable objects, declared actions
   ▼
Available actions spec.actions ∩ enabled in connection.config
   ▼
Automation        fixed rules in code, not a rule builder:
                    a settled call (a fact)                    → ADD_NOTE   (always on for a connected ATS)
                    a person's decision: reviewed / declined   → SET_STAGE  (E2: opt-in, customer-mapped, level-triggered, from a baseline)
                    custom connection                          → events feed (webhooks later)
   ▼
Agent             the voice agent never calls an action. It receives only the compiled job, questions and knowledge.
```

**Provider independence of the core agent.** FACT: data reaches a live call only at provisioning, and the live agent gets only `end_call`, `voicemail_detection` and `transfer_to_number` (`JAVA/engine/CallContextCompiler.java` lines 26-37, 220-237).

**Where the never-recommend rule is enforced (three places, all testable):** content (only `ExternalPayloads`, no summary); trigger (`SET_STAGE` sends only the candidate's current `screening_status`, only `reviewed` or `declined`, set only by a person through the stage routes, FACT `JAVA/hiring/Jobs.java` line 264; API keys cannot change stages; a call outcome never moves an ATS status); target (adapters expose only `addNote` and `setStage`). The live call itself is protected by the prompt fence fix (section 11.1 item 9).

**Stage write-back (slice E2; from a baseline, level-triggered).** Off by default. It ships after E1 (import, notes, closed rows), behind its existing switch, once founder decision 7 is answered (round 9 EIA-4, UX-4: it is the most rule-dense part of E and is not needed for results to flow back). The customer picks the target status for "Moved forward" and "Not moving forward" from their live status list.
- **Baseline.** Only decisions made after write-back is on, or after a row was linked, are sent (`pushed_stage` as section 2.3). Earlier decisions are never sent in bulk. **A reconnect re-baselines too** (round 7 CR-1, UX-1): the transaction that moves `connected_at` runs the same UPDATE as switching write-back on (`pushed_stage` = the current stage for the connection's links), so decisions made while the card said "Not connected" are never written; the reconnect screen says "Decisions made while disconnected are not sent to Zoho Recruit." **That UPDATE also closes the connection's `pending` and `failed` stage rows** (`status = 'sent'`, `last_error_code = 'skipped'`, `content_hash` = the link's new `pushed_stage`), so no card line or Retry is left for a decision the screen said would not be sent (round 8 BE-6). Recovering from `needs_attention` (new consent, Take over) does not re-baseline: those decisions were made while the footer promised a write, and they are still sent, under the rules below and the 7-day expiry.
- **Discovery** (the tick, for connections that are not `disconnected`, have write-back on and are not `needs_attention` with `status_unmapped`): candidates with a live link where the current stage is `reviewed`/`declined` and differs from `pushed_stage`, or is `new`/`screening` while `pushed_stage` is `reviewed`/`declined`. Upsert their stage row: `content_hash` = the current stage, `status = 'pending'`, `attempts = 0`, `next_attempt_at = candidates.updated_at + interval '2 minutes'` (the hold), when `content_hash` differs.
- **The handler** (inside `send:<connectionId>`, same refusal and backoff rules as notes):
  1. **Hold.** If `candidates.updated_at` is less than 2 minutes ago, move `next_attempt_at` to 2 minutes after it and leave the row. The in-app Undo lasts 8 seconds and re-posts the previous stage (FACT, `apps/web/components/ui/toaster.tsx` line 78; `apps/web/app/jobs/[id]/candidates/page.tsx` lines 680-698), which moves `updated_at` again. A person's contact edit also moves it (FACT, `JAVA/hiring/Candidates.java` line 113); that only delays the push. The pull never moves it (section 5). Otherwise read the candidate's current stage **S** and the row's hash **H**.
  2. **Switch, read at send time, and nothing to send** (round 7 BE-1). The run has reloaded the connection: if write-back is now off, or S is `reviewed`/`declined` and its target status is not mapped, close the row without calling the ATS (`skipped`). Close it the same way if S equals `pushed_stage` (for example, undone within the hold), or if S and `pushed_stage` are both `new`/`screening` (nothing was ever sent).
  3. **Read the application live** (`getApplication`: its status, and whether it is open or closed in the ATS).
     - **Already at target** (S is `reviewed`/`declined`): its status equals the mapped target of S (for example our own write just before a crash): no note, no `setStage`.
     - **Forward** (S is `reviewed`/`declined`): call `setStage` with the comment "Moved forward by Priya Sharma in HRVoice" **only if the application is open and its live status is either the connection's trigger status (where it was when we brought it in) or the mapped target of `pushed_stage` (the status HRVoice last wrote)**. In every other case write a note instead and leave the status alone (`note_only`): "Not moving forward (decided by Priya Sharma in HRVoice). The status in Zoho Recruit was left as it is; update it there if needed." ("Moved forward" likewise). The note makes no claim about who set the current status, so it is true whether the status was moved on in the ATS, the application is closed there, the trigger status was changed in HRVoice, or an earlier decision was withdrawn (round 8 IA-3, CR-5). FACT why not compare with `remote_status_seen`: every 15-minute pull refreshes it for every linked application (section 5), so that check caught only changes made since the last pull (round 7 CR-1, UX-1, EIA-2). `remote_status_seen` is for display only.
     - **Withdrawn** (S is `new`/`screening` while `pushed_stage` is `reviewed`/`declined`): a note "Decision withdrawn in HRVoice by Priya Sharma. The status in Zoho Recruit was left as it is." (`note_only`).
     - **Every note on this path** ends with the marker `HRVoice ref s<candidate prefix>.<stage hash prefix>`, checked by the same rule as call notes (markers listed only after an uncertain attempt, section 5), so a timeout on a write Zoho actually committed does not give a second note (round 9 BE-3, round 10 CR-4).
  4. **One rule for every close** (round 7 IA-1; round 8 BE-3, IA-3, CR-4). First `pushed_stage` := S, **written unconditionally**: it records what this run handled, even if the decision changed during the call to the ATS. Then the row: `status = 'sent'`, `sent_at`, `attempts = 0`, `last_error_code` (NULL, `note_only` or `skipped`) and `content_hash = S`, as a compare-and-set on H. So a later decision always differs from the stored hash and is discovered (decide, Undo, decide again sends exactly once); a decision made during the send leaves the row `pending`, and the next run judges it against the status that was really written; and a row closed at step 2 is not rediscovered every minute, because its hash and `pushed_stage` both equal the current stage. A row that fails permanently or expires keeps its target as its hash, so it is not retried until the decision changes.
- **A status-map edit does not re-baseline** (round 9 BE-6, CR-1). In v9 it did, so a decision made while a renamed status left the connection `status_unmapped` was marked handled when an admin remapped, and nothing was ever written or shown. Now pending rows are judged at send time under the current map; a status written under the old map no longer equals the mapped target of `pushed_stage`, so the result falls back to a note, the safe direction. Re-baselining happens only when write-back is switched on and on reconnect, both of which say so on screen.
- **The allowlist is deliberately not widened** to both mapped targets (round 8 IA-3 a): customers usually map "Moved forward" to a status their team also sets by hand, so a decline in HRVoice would overwrite a move made in Zoho and could email a rejection (the round-7 CR-1 harm). Cost: a written decision that is withdrawn and later reversed arrives as a note, and the decision line says so.
- **The decider's name** (round 7 SA-5, BE-2) comes from the latest `hiring.candidate_status_changed` audit row for that candidate and job **whose `from` differs from its `to`**, used only if that row's `to` equals the stage being sent: the person's display name (`users.name`). Otherwise, or when the name is empty or the row is missing, "a team member". Never an email. FACT: the route writes an audit row for every update in the request, including ones that did not change the stage, after the stage transaction, and `AuditService.record` swallows failures (`JAVA/hiring/Jobs.java` lines 255-269; `JAVA/hiring/HiringController.java` lines 362-396; `JAVA/audit/AuditService.java`). So a no-op re-post by Bob cannot be named as the decision, and when Bob's real change has no audit row, the newest real change points at some other stage and the comment says "a team member", never an earlier decider.
- Because the handler reads current state, retries cannot leave the ATS on an older decision.
- `ponytail:` if a customer's ATS moves new applications on by itself after import (an automation), every decision for those people arrives as a note, not a status. Upgrade if a pilot hits it: store the ATS status the decider saw on the stage row and allow overwriting exactly that (round 7 UX-1's column).

**Notes.** One per call, a follow-up only if the rendered note changed (section 6.1):

```
Outcome: Call completed            (or: No answer / Reached voicemail / Picked up, didn't speak / Number not valid / Result unavailable)
```

- **Workspace deletion (Core part):** the connection's token is revoked at `FakeAts` after commit, and the hard delete succeeds.
- **Hard delete** of an org with an agent session, a voice session, a ledger row, a connection, a job link, a candidate link and a note and a stage delivery row (Dev adds an API key and an event).
- **Linked fields:** editing an ATS-linked phone is refused with `candidates.managed_externally` while connected, allowed after disconnect.
- **Removing a linked person**, through the existing `DELETE /candidates/{id}` route (round 9 BE-5): anonymised (placeholder name; NULL phone, email, resume text), content deleted, the next `FakeAts` pull does not import it again (`removed_in_hrvoice`); the link is cleared; no send reaches it. **Reconnect** reuses the connection row and keeps the suppression; relinking the Zoho job to another HRVoice job does not import them either (round 9 IA-3).
- **Deleted in the ATS** (round 9 EIA-1, SA-1): with the nightly listing, applications deleted in `FakeAts`, for good or to its recycle bin, become `missing` at the next complete listing, are not dialed and get no note; without it, they stay `open`; nothing is anonymised and nothing is deleted at `FakeVoice`, however long they stay missing; restored, they go back to `open`. **Merge:** `FakeAts` merges the candidate into another while the application stays listed: nothing is anonymised or deleted, `external_parent_id` becomes the master's id at the next pull, and a note refused as `NotFound` before that is delivered to the master record with no Retry (round 10 EIA-3).
- **Nightly listing** (round 8 IA-4, EIA-5, UX-4, BE-4, CR-3): a 5xx on page 2 marks no link `missing`; a link a concurrent pull creates during the listing stays `open`. With more linked jobs than one run's budget allows, every job is listed by the end of the day and none twice; a job that always fails is tried at most once an hour; a `missing` link seen again is `open` (round 9 BE-1, CR-3); an anonymised link stays `deleted` after a complete listing, and "Remove this person" committing during a listing leaves the row anonymised (round 10 IA-2, SA-1). Built only if spike item (a) succeeds.

## 14. First real integration and how to test it without buying anything

### 14.1 Choice

- Slices 0 and A help every customer now; item G protects every customer's calling.
- **Zoho Recruit is the first named connector** if a pilot uses it: self-serve OAuth, an India data centre, a documented REST API with incremental polling, and a free plan with API access. The evidence that Indian SMBs use it is vendor-written, so the founder confirms with pilots first.
- The developer surface is first only if a pilot has a developer or an iPaaS.

### 14.2 Testing without buying anything

- **Automated:** the existing JUnit 5 + Testcontainers suite plus the merge-blocking tests in section 11.1, using `FakeVoice` (lost webhook, stuck `active`, silent call, unreachable provider, delete conversation) and `FakeAts` (baseline, Undo, rename, rate limit, delete and restore, merge, partial listing, always-failing note, 422, large page, a mobile fixed only on the Candidate, a page shift mid-scan, a colliding linked phone).
- **Manual push-in:** `curl` and the reference Python script against a local Java API. **Pull-out:** the reference script polling `/v1/events`.
- **iPaaS path:** self-hosted n8n, free edition, polling the feed (FACT, https://docs.n8n.io/deploy/host-n8n).
- **Zoho:** a Zoho Recruit Free account in the India data centre (FACT: 1 active job, 5,000 API credits a day, no webhooks, https://www.zoho.com/recruit/plan-comparison.html); one Web-Based OAuth client per environment (https://www.zoho.com/recruit/developer-guide/apiv2/register-client.html); 5-10 test candidates using team members' own numbers with their consent.
- **Voice provider, on a test account (gate P):** when a phone call's configuration binds, by dialing a second job on the same agent during a live call (R18).
- **Spreadsheets:** open the results CSV in Excel (Windows) and Google Sheets, with a Hindi answer and phone numbers.

Not testable for free: Zoho webhooks; custom-status behaviour on paid plans; Keka, Greenhouse, Lever, Darwinbox.

## 18. ADR-010 (one invariant per rule; round 10 AM-5; five rules sharpened in round 12)

This section is ADR-010 as it should be written: each rule is one invariant. The mechanism that keeps it, and its test, are in the section named and go into the slice's build sheet, not into the ADR.

**Gates**
1. No slice reaches customers before Java serves production (gate P), which includes the hosted-adapter fix-up, an external uptime monitor and three supervised live checks (R18, a conversation id on every accepted dial, provider delete with the production key); a failed R18 check blocks quoting E until the founder picks a fix (section 13.1).
2. Core is built only with E or Dev and goes live only once Nest is no longer routed in production; from then, rollback is a Java image rollback (section 13.1).
3. Removal, the one erasure path, provider deletes and the DPA go live before the first external connection (section 11.1 item 10).
4. Self-serve calling (item G, decision 15) and retention, workspace deletion and restore (item W, decision 16) are risks that exist today; this plan records them and does not design them (section 13.1).

**Tenancy and identity**
5. Every new table has forced row-level security on `organization_id`, is in `StructuralTest`, and cascades every foreign key; the tenant comes only from server state (sections 2.3, 10).
6. An API key acts only as a bearer header on `/v1` handlers on `API_PUBLIC_HOST`, with the key's permissions intersected with its creator's live ones, and `/v1` code never re-reads `role_permissions` (Dev; sections 6.6, 10).
7. Workers act as `inOrg(org, Db.NIL)` with a NULL audit actor, and every integration idempotency key contains an organisation or connection UUID (sections 6.8, 10).

**Product rule**
8. Only `ExternalPayloads` builds what leaves HRVoice, and it never carries a summary, score, coverage, rank or recommendation; answers come only from the job's own questions, as capped plain text or "No answer noted; check the recording" (section 6.2).
9. Only a named person's decision moves an ATS status, and only where that status is still where HRVoice found it or last put it; otherwise a note that claims nothing about who set the status (E2; section 7).
10. Machine-sourced text is fenced before it reaches a prompt, extraction never rates the candidate, and agent linking stays human (section 11.1 item 9).

**Sync and delivery (Core + E1; stage rows from E2)**
11. Each field flows one way: contact fields in (owned by the ATS on linked rows, and corrected from it), job text copied once, results and decisions out (sections 4, 5).
12. One inbound record never stops another, an unexpected error included, and a record HRVoice could not take is listed with its fix and taken when it changes; a job linked at any time brings in its people at the trigger status, not only those changed since the last scan (section 5).
13. Every change in the ATS is read by two completed scans, and a scan cut short never moves the window (section 5).
14. Outbound to an ATS is one row per call or per candidate stage, each with its own backoff and no order; a row that throws backs off like any other; nothing is sent for a person whose link is not live, whose call is erased, or whose connection was disconnected mid-run; a note already sent is never sent again because a job was unlinked and relinked; anything unsent after 7 days is shown (sections 5, 6.1, 7).
15. Nothing the ATS does erases a person in HRVoice, and no listing ever touches an anonymised link (section 5).

**Events (Dev only)**
16. In an org with a feed, the events lock is the first statement of every emitting transaction; `seq` per org never goes down, `410` is defined against the oldest retained `seq`, and an undone stage event is marked `superseded` (section 6.5).

**Background work**
17. Every dial is one person's click through `startOutbound` and `dialLocked`; this plan adds no bulk or automatic dialing, and a dial it refuses never re-provisions a hosted agent (sections 5, 10).
18. The tick and the 5-minute loop do database work only, enqueue after commit and catch errors per org; all vendor and provider HTTP runs on the integration lane, within a per-run budget, stopping at the first timeout or 5xx, taking items in an order no single failing item can monopolise; a lane thread claims only what it runs, survives any error, and depends on no Spring scheduler thread (section 6.8).
19. `JOBS_ENABLED=false` stops all background work, emails included; a problem with one customer's ATS is handled by that connection's Disconnect (section 6.8).

**Data protection**
20. One erasure path, through `DELETE /candidates/{id}` and (Dev) a `/v1` deletion; no other code deletes a candidate or job row; an anonymised ATS link keeps only a keyed suppression hash, checked per connection, whose key never rotates (section 11.1 item 10).
21. Secrets live only in `secrets_sealed` and are never overwritten by an older token; a replaced token is revoked at the vendor; no vendor call runs under the grant of a person who lost access; raw vendor bodies and database error details never reach logs or `last_error`; audit rows store route templates and are kept (sections 5, 10, 11.1).
22. Until Nest is no longer routed in production, migrations only add things Nest ignores (R10).
